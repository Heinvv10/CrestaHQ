# Bulk email broadcasts (v1)

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

The contacts page exposes a **Send bulk email** action that fans out a chosen email template to a filtered audience (all contacts / a specific tag / a pipeline stage). Implementation reuses the automations infrastructure — same template engine, same merge tags, same QStash for fan-out, same `{{unsubscribeLink}}` opt-out path.

- **UI**: [src/components/contacts/bulk-email-dialog.tsx](../../src/components/contacts/bulk-email-dialog.tsx) lets the operator pick template + audience filter and shows a live recipients/skipped preview computed from the loaded contact list. Confirm posts to `/api/broadcasts/email/send` and routes to the broadcast detail page.
- **Send route**: [src/app/api/broadcasts/email/send/route.ts](../../src/app/api/broadcasts/email/send/route.ts) validates the template (must be type `email`, must contain `{{unsubscribeLink}}`), sizes the audience (an aggregate `count()`, or for a territory-scoped collaborator a projected scan of their territories only; hard cap 25,000, counted before opt-out skips; empty → 400), creates the `broadcasts/{id}` parent doc and publishes ONE fanout message, then returns. The request never loads the audience or publishes per recipient, so it cannot outlive the proxy timeout. The dialog sends a client-generated `idempotencyKey`; the broadcast doc id is `{subAccountId}_{key}` and is created with `create()`, so a retried or double-clicked submit returns the existing broadcast instead of emailing everyone again. A retry of a broadcast whose fan-out never started re-publishes the start (fixed dedup id); a retry of a failed start stays a 502.
- **Fanout step**: [src/app/api/broadcasts/email/fanout/route.ts](../../src/app/api/broadcasts/email/fanout/route.ts) is a self-rescheduling QStash callback (same shape as the GHL import drain). Each call reads one page of 200 contacts via [src/lib/broadcasts/audience.ts](../../src/lib/broadcasts/audience.ts) (pre-skips opted-out + missing-email contacts), creates their `sends/{contactId}` rows and bumps totals in one batch, and publishes one staggered `/step` message per recipient at 5/sec. A publish that fails marks its row `failed`, so the broadcast still completes. A redelivered page re-publishes every still-queued row in its id range (the step re-checks the contact), and a page still failing on its final QStash retry ends the fan-out there: the broadcast completes with what was queued (still cancellable meanwhile) and `errorMessage` says where it stopped. Step messages publish with the same explicit retry budget. `fanoutDone` gates completion until the last page has run.
- **Step executor**: [src/app/api/broadcasts/email/step/route.ts](../../src/app/api/broadcasts/email/step/route.ts) is the per-recipient QStash callback. Verifies signature, then **claims** the send row in a transaction ([claim-send.ts](../../src/lib/broadcasts/claim-send.ts)) — a redelivery or concurrent duplicate never sends twice. A failure before the provider call releases the claim so QStash's retry re-runs the row; a delivery finding a fresh claim answers 503 so QStash keeps retrying; a stale claim (10 min) is failed as "delivery unknown", never re-sent; the settle is a transaction that only lands while the row is still queued under this step's `claimId` (so a late original never overwrites a stale-failed row), retried in-process. At send time it re-checks the agency gate (`broadcastsEnabledByAgency`), the `automationsPaused` kill switch (both settle the row `skipped` with a reason), a disconnected sender (row `failed`, reason shown), and `contact.emailOptedOut`; renders merge tags, sends, writes the row's status + atomically increments parent totals. Failed sends are recorded as `status: "failed"` and return 200 — one bounce never retry-storms the batch. The fanout and step routes are in `PUBLIC_PATHS`; security is the QStash signature.
- **Cancel**: `POST /api/broadcasts/email/cancel` with `{ broadcastId, subAccountId }` (Cancel button on the detail page; membership is checked before the broadcast is looked up) flips the broadcast to `cancelled`. The fanout stops paging and every still-queued row settles as `skipped: cancelled` when its message fires. A row already claimed when the cancel lands still sends.
- **List + detail pages**: `/sa/[id]/broadcasts` and `/sa/[id]/broadcasts/[broadcastId]` — onSnapshot-driven, so totals and per-recipient status update live as the fan-out drains.
- **Compliance**: every bulk email goes through the same `validateEmailBody` check that requires `{{unsubscribeLink}}` (CAN-SPAM). Per-recipient unsubscribe links resolve at `/u/[token]`, HMAC-signed with `AUTOMATIONS_TOKEN_SECRET`, flip `contact.emailOptedOut` on click. Pre-flight + live opt-out checks ensure opted-out contacts are never sent. A recipient on the sub-account's [email suppression list](email-providers.md#suppression-list) is settled as `skipped` / `suppressed` at send time.
- **Open & click tracking** (W4 PR2, [spec](../programme/w4-email-tracking.md#pr2-open-pixel-and-click-redirect)): two switches per sub-account in Settings → Messaging → *Broadcast open & click tracking*, both **off by default** (`subAccounts/{id}.emailTracking.{opens,clicks}`, set through `PATCH /api/agency/sub-accounts/[id]`). With both off the HTML body is byte-identical to an untracked send. Clicks on: the step ([email-tracking.ts](../../src/lib/broadcasts/email-tracking.ts)) rewrites each http(s) `<a href>` to `/t/c/{token}` and stores the destination at `broadcasts/{id}/links/{linkKey}` before sending; unsubscribe (`/u/…` on this host), `mailto:`, `tel:`, relative and other schemes are left alone, as is the plain-text part. Opens on: one 1×1 pixel `/t/o/{token}` at the end of the body. Tokens are HMAC-signed (`AUTOMATIONS_TOKEN_SECRET`, purpose-prefixed) over `broadcastId.contactId[.linkKey]`. `/t/c/` 302s only to the stored destination (re-validated http(s)) and 404s on any bad token; `/t/o/` always returns the GIF. Each records first open / first click on the send row and an `email_opened` / `email_clicked` contact activity ([engagement.ts](../../src/lib/broadcasts/engagement.ts)), only while the row is `sent` and that switch is still on. The redirect and the pixel never wait on a limiter; only the record step is limited, 20/min per token (not per IP: Gmail and Apple fetch through shared proxies). Caps: 50 tracked links per email, 500 link docs per broadcast (a merge-tagged href makes one per distinct rendered URL), bodies over 500,000 characters go out untracked. **Opens are an estimate**: Apple Mail Privacy Protection preloads images, and link scanners can inflate clicks. **NOT runtime-verified**: needs the live walk (a #1000 broadcast to the owner's own address). No stats UI or workflow triggers yet (I3).
- **Quiet hours** do not apply: they hold automated SMS and WhatsApp only (see [workflows](workflows.md)), and broadcasts are email.
- **No SMS broadcasts in v1** — bulk SMS needs A2P 10DLC throughput awareness, consent-source audit fields, and TCPA-grade safeguards that are explicitly deferred to Phase 2.
