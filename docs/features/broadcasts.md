# Bulk email broadcasts (v1)

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

The contacts page exposes a **Send bulk email** action that fans out a chosen email template to a filtered audience (all contacts / a specific tag / a pipeline stage). Implementation reuses the automations infrastructure — same template engine, same merge tags, same QStash for fan-out, same `{{unsubscribeLink}}` opt-out path.

- **UI**: [src/components/contacts/bulk-email-dialog.tsx](../../src/components/contacts/bulk-email-dialog.tsx) lets the operator pick template + audience filter and shows a live recipients/skipped preview computed from the loaded contact list. Confirm posts to `/api/broadcasts/email/send` and routes to the broadcast detail page.
- **Send route**: [src/app/api/broadcasts/email/send/route.ts](../../src/app/api/broadcasts/email/send/route.ts) validates the template (must be type `email`, must contain `{{unsubscribeLink}}`), sizes the audience with an aggregate `count()` (hard cap 25,000, counted before opt-out skips), creates the `broadcasts/{id}` parent doc and publishes ONE fanout message, then returns. The request never loads the audience or publishes per recipient, so it cannot outlive the proxy timeout. The dialog sends a client-generated `idempotencyKey`; the broadcast doc id is `{subAccountId}_{key}` and is created with `create()`, so a retried or double-clicked submit returns the existing broadcast instead of emailing everyone again.
- **Fanout step**: [src/app/api/broadcasts/email/fanout/route.ts](../../src/app/api/broadcasts/email/fanout/route.ts) is a self-rescheduling QStash callback (same shape as the GHL import drain). Each call reads one page of 200 contacts via [src/lib/broadcasts/audience.ts](../../src/lib/broadcasts/audience.ts) (pre-skips opted-out + missing-email contacts), creates their `sends/{contactId}` rows and bumps totals in one batch, and publishes one staggered `/step` message per recipient at 5/sec. A publish that fails marks its row `failed`, so the broadcast still completes. `fanoutDone` gates completion until the last page has run.
- **Step executor**: [src/app/api/broadcasts/email/step/route.ts](../../src/app/api/broadcasts/email/step/route.ts) is the per-recipient QStash callback. Verifies signature, then **claims** the send row in a transaction ([claim-send.ts](../../src/lib/broadcasts/claim-send.ts)) — a redelivery or concurrent duplicate never sends twice; a claim left by a crashed step is failed after 10 min, not re-sent. At send time it re-checks the agency gate (`broadcastsEnabledByAgency`), the `automationsPaused` kill switch (both settle the row `skipped` with a reason), a disconnected sender (row `failed`, reason shown), and `contact.emailOptedOut`; renders merge tags, sends, writes the row's status + atomically increments parent totals. Failed sends are recorded as `status: "failed"` and return 200 — one bounce never retry-storms the batch. The fanout and step routes are in `PUBLIC_PATHS`; security is the QStash signature.
- **Cancel**: `POST /api/broadcasts/email/cancel` (Cancel button on the detail page) flips the broadcast to `cancelled`. The fanout stops paging and every still-queued row settles as `skipped: cancelled` when its message fires. A row already claimed when the cancel lands still sends.
- **List + detail pages**: `/sa/[id]/broadcasts` and `/sa/[id]/broadcasts/[broadcastId]` — onSnapshot-driven, so totals and per-recipient status update live as the fan-out drains.
- **Compliance**: every bulk email goes through the same `validateEmailBody` check that requires `{{unsubscribeLink}}` (CAN-SPAM). Per-recipient unsubscribe links resolve at `/u/[token]`, HMAC-signed with `AUTOMATIONS_TOKEN_SECRET`, flip `contact.emailOptedOut` on click. Pre-flight + live opt-out checks ensure opted-out contacts are never sent. A recipient on the sub-account's [email suppression list](email-providers.md#suppression-list) is settled as `skipped` / `suppressed` at send time.
- **No SMS broadcasts in v1** — bulk SMS needs A2P 10DLC throughput awareness, consent-source audit fields, and TCPA-grade safeguards that are explicitly deferred to Phase 2.
