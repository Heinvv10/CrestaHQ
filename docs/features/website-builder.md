# Website builder (gitpage.site v1)

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

Each sub-account can hold **up to `MAX_WEBSITES_PER_SUBACCOUNT` (5)** website docs at `subAccounts/{id}/website/{siteId}` (see [src/lib/website/limits.ts](../../src/lib/website/limits.ts)). The legacy singleton at `.../website/main` remains valid as one of the slots — no migration. The page at [my-ghl-app/src/app/(dashboard)/sa/[subAccountId]/website/page.tsx](../../src/app/(dashboard)/sa/[subAccountId]/website/page.tsx) owns the collection `onSnapshot` + the "Add website" affordance + the account-wide activation gate, and renders one card per site via [src/components/website/website-builder.tsx](../../src/components/website/website-builder.tsx). Each `<WebsiteBuilder/>` holds its own form (a long sectioned form mirroring gitpage's typeform inputs — Basics / Pages / Services / Business / Design / FAQ), collapse state, and build/status logic; the parent passes the live doc down (one listener, not one per card). Cap is enforced server-side in `POST /api/sub-accounts/[id]/website` (the create-site route, returns 409 on the 6th). Site cards expose a **Remove** (trash) action that deletes the doc to free a slot — distinct from **Rebuild** (reset to draft).

- **Submit**: [src/lib/gitpage/client.ts](../../src/lib/gitpage/client.ts) `submitBuild()` POSTs to `https://www.gitpage.site/api/v1/generate-site` with `buildType: "local" | "vsl"` (selected by the user via the **Site type** picker on the page) and the agency's `GITPAGE_API_KEY`. Returns 202 + `formResponseId` (prefixed `build_…`). The build route persists `status: "queued"` and the job id, then schedules the first QStash poll. v1 contract is frozen — additions ship into v1, breaking changes land at `/api/v2/`.
- **Build types**: `local` is the multi-page LocalSite (home + optional services/contact/terms). `vsl` is a single-page Video Sales Letter funnel — hero + embedded video + bullets + one CTA. The VSL form drops the Pages/Services/Business sections and shows a Video section instead; `video_link` (any http(s) embed URL — YouTube/Vimeo/Wistia) is required, and `cta_link` is mandatory because the funnel collapses without a destination after the video. Mode is stored on `WebsiteConfig.build_type`; existing docs without it default to `"local"` on read.
- **Polling**: [src/app/api/sub-accounts/[id]/website/[siteId]/poll/route.ts](../../src/app/api/sub-accounts/[id]/website/[siteId]/poll/route.ts) is a QStash signature-verified callback that hits gitpage's status endpoint every 20s (40s after five minutes), mirrors the result into Firestore, and reschedules itself until terminal (Published/failed) or the cap derived from gitpage's duration estimate (45 ticks for a job with no estimate, up to 120 — see [Premium builds](#premium-builds-website-build-v2--not-runtime-verified)). A terminal result is handed to `settleWebsiteBuild()`. The QStash payload carries `siteId` (verified against the path) so each site polls its own doc; dedup ids are namespaced by `siteId`. The route is in PUBLIC_PATH_PATTERNS in middleware (regex now `…/website/[^/]+/poll`) because security comes from the signature, not the session cookie.
- **Field name mapping**: internal types use snake_case (matches the rest of the codebase); the gitpage client transforms to camelCase + flat `pages` array at submit time.
- **Design fields**: dropdowns with gitpage's curated values (see [src/lib/website/gitpage-values.ts](../../src/lib/website/gitpage-values.ts)). gitpage silently falls back to defaults on unknown values, which would look broken — dropdowns prevent that.
- **Custom palette** requires a 3-hex triple in `customColors`; conditional input appears when `design_color_palette === "Custom"`.
- **Rebuild vs Remove**: `DELETE /api/sub-accounts/[id]/website/[siteId]?reset=1` resets the doc to `draft` (preserves config, clears jobId/liveUrl/status) — the Rebuild button. `DELETE /api/sub-accounts/[id]/website/[siteId]` (no flag) permanently removes the doc to free a slot — the Remove button. Either way the previously-published GitHub repo stays live until manually deleted on gitpage's side — v1 doesn't tear down.
- **Auth model**: one `GITPAGE_API_KEY` per agency; shared across all sub-accounts. Each build's `subAccountId` is sent so gitpage tags the build record. Filter all reads/writes by sub-account on our side — gitpage scopes by agency, not sub-account.
- **Rate limit**: gitpage caps at 30 builds/hour/agency. v1 doesn't add a client-side cap; gitpage returns 429 with `resetAt` when exceeded.
- **Heartbeat / subscription gate**: [src/lib/gitpage/heartbeat.ts](../../src/lib/gitpage/heartbeat.ts) `sendHeartbeat()` checks the deployment's website-builder subscription. The response includes `gitpageStatus.agency: boolean` which gets cached at `system/gitpageStatus`. The website-builder UI reads that doc via `onSnapshot` and renders an "activate" banner when `agency === false`. Fired once per cold start via [instrumentation.ts](../../instrumentation.ts) and once daily via QStash → [/api/cron/gitpage-heartbeat](../../src/app/api/cron/gitpage-heartbeat/route.ts) (signature-verified). To set up the daily schedule: in Upstash QStash dashboard create a schedule pointing at `${NEXT_PUBLIC_APP_URL}/api/cron/gitpage-heartbeat` with cron `0 3 * * *`.

## Premium builds (Website Build v2 — NOT runtime-verified)

**Status: ported from upstream 1.0.40, merged dark, never run against gitpage.** Production has no `GITPAGE_API_KEY` and `websiteEnabledByAgency` is off for every sub-account, so nothing below has built a real site. The first client to enable the builder triggers a live walk. The port is split into seven units (`UPSTREAM_PORT_PLAN.md`, P3); this section describes what is on `main` and names what is not.

Premium is gitpage's staged build: one of three authored design directions ("concepts") per niche, copy written from the operator's facts, generated photography. gitpage estimates 20 minutes (`estimatedDurationSeconds: 1200`).

**Shipped (units WS-1 and WS-2):**

- **Every build is premium.** `normalizeWebsiteConfig` forces `quality: "premium"`, so a draft saved as `standard` builds as premium. The premium flags default on (`include_form`, `include_chat`, `include_voice`); a blank concept is stored as `null` and gitpage picks the niche default. The current form has no premium inputs yet (WS-5/WS-6), so a build today sends an empty premium block.
- **Request** ([lib/gitpage/client.ts](../../src/lib/gitpage/client.ts)): premium adds `quality`, `claudeModel: "opus-5.5"` (`PREMIUM_CLAUDE_MODEL`, forced whatever the agency's gitpage dashboard says), a `premium` block (concept, `mode` from the colour scheme, `heroMotion`, and the typed facts parsed by [lib/website/premium.ts](../../src/lib/website/premium.ts)), optional `referenceNotes`, `editorEmail` (the builder's Firebase Auth email, lower-cased; gitpage invites it as an editor of the new site) and `callbackUrl`. The callback URL is sent only when `NEXT_PUBLIC_APP_URL` is a bare `https://host` origin. The client can also send the `leadstack` wiring block (form + chat widget URLs), but nothing passes one yet — see WS-3 below.
- **One guarded write.** Every write to a site doc's build state goes through `transitionWebsite(docRef, { expectJobId, fromStatuses, when }, patch)` in [websites-service.ts](../../src/lib/server/websites-service.ts): it re-reads the doc in a transaction and applies only if the doc still carries the job the writer acted for and is in a status that writer may move it from; otherwise it is a no-op and the writer stops (no reschedule, no hand-off). Five writers race on the doc — the poll tick, **Re-check now**, the callback, the draft save, and a build submit or reset — and each reads, then spends up to seconds on gitpage or QStash, then writes. So: `ready` is never written over, and never becomes `failed` (a 4xx, the cap timeout, a failed reschedule); an in-flight bump never lands on a settled doc; an old job's tick cannot touch the job that replaced it; a reset during a tick leaves a draft with no job, not `building` with none. Upstream uses plain updates throughout; this is a deliberate difference, because the WS-3 hand-off creates a workflow that messages leads and must run once.
- **Settle.** `settleWebsiteBuild()` is the ONE terminal handler, shared by the QStash poll tick, **Re-check now** and the callback. It writes `status`, `liveUrl`, `statusPhase`, `conceptName`, `gitpagePageId`, `pollAttempts` and `settledDelivery` (`{jobId, status}`: the report it applied). It applies while the site is queued or building — or `failed` when the caller is the manual re-check, or when gitpage now reports Published after the poll cap gave up. A caller that loses returns `"noop"`. Two more no-ops: **Published without a usable live URL** is not settled (a site is never `ready` with no address; the poll comes back for it), and **a repeat of the report already applied** for that job is ignored, so a replayed callback cannot re-fail a build the operator has resumed.
- **Callback.** `POST /api/webhooks/gitpage/build-settled` ([route](../../src/app/api/webhooks/gitpage/build-settled/route.ts)) is public (in `PUBLIC_PATH_PATTERNS`, exact path). Its only credential is `X-Gitpage-Signature: sha256=<hex>`, the HMAC-SHA256 of the RAW body under `GITPAGE_API_KEY`, compared in constant time before the body is parsed. The body is capped at 64 KB (Content-Length, then the bytes as read) BEFORE the HMAC is computed: 413 over it. A bad or missing signature is 401; no key on the deployment is 503; everything else is 200 (`settled` or `ignored: <reason>`) so gitpage never retries in a storm. The site is found by `gitpageJobId` inside the `subAccountId` the signed body names (which must be a document id, never a path). A signed body is still outside data: a `status` that is not a string reads as in flight; the live URL is kept only if it has no whitespace or control characters, parses, is `https:`, carries no credentials, is not localhost or a non-public IP literal, and is at most 2,048 characters; error and stage text, the partial-error list and the page id are length-capped (`normalisePollBody` in the client, so the poll's answer is held to the same rules). The poll loop keeps running alongside it.
- **Polling.** The cap is `pollAttemptCapFor(estimatedDurationSeconds)`: 1.5× the estimate at the 20s cadence, clamped to 45–120 ticks (90 for a 20-minute premium estimate). `pollDelayFor` backs off from 20s to 40s once 15 ticks have run. `WebsiteDoc.statusPhase` mirrors gitpage's stage on every in-flight tick. A tick whose write does not apply (see One guarded write) answers `stale-tick` and does not reschedule. **Re-check now** starts a new poll chain only when it resumes a `failed` site that gitpage is still building; on a site already queued or building it refreshes the stage and nothing else, so repeated clicks cannot multiply chains or push the cap out. (Before, every click reset the attempt count and added a chain. A chain that has died while the doc still says building is therefore no longer restarted by a click: the click still settles the site once gitpage has finished, and so does the callback.)
- **Draft save.** `PATCH /api/sub-accounts/[id]/website/[siteId]` (`{config, wizardStep}`, sub-account admin) stores a partial config and the wizard step to resume on. It is refused with 409 while the site is queued or building, and while it is `failed` but still carries its job id — a re-check or a late callback can still make that build the live site, and the stored config must be the one it was built from. The check and the write are one transaction. It never touches status, job id or live URL. Gated: 403 when `websiteEnabledByAgency` is off. Nothing calls it until the wizard (WS-6); **WS-6 note:** upstream's wizard saves the draft when a failed build is reopened with Try again, which this now refuses until the site is reset.
- **Build limits.** `submitWebsiteBuildForSubAccount` answers 409 for a site that is already queued or building (checked before gitpage is called, and again atomically with the write), 409 for a build on a new site id once the sub-account is at `MAX_WEBSITES_PER_SUBACCOUNT`, and 429 with `Retry-After` past `WEBSITE_BUILDS_PER_HOUR` (10) submits per sub-account per hour — gitpage's own cap of 30 an hour is per agency, so one workspace could otherwise use every other workspace's builds. The hourly limit is the in-memory `createFixedWindowLimiter` (per instance, resets on a cold start), as the AI test panel uses. Two submits for one site that arrive in the same instant can still both reach gitpage; one takes the site, the other gets 409 and its gitpage build is orphaned (logged), bounded by the hourly limit.
- **Concepts.** `GET /api/sub-accounts/[id]/website/concepts?niche=…` is a member-authed proxy over gitpage's `GET /api/v1/concepts`; the agency key never reaches the browser. Gated: 403 when `websiteEnabledByAgency` is off. Nothing calls it until the concept picker (WS-5).

**The agency gate.** `websiteEnabledByAgency` stops new work: create, build, the draft save and the concepts proxy all answer 403 with the same message (upstream gates only create and build). It is deliberately not checked where a build finishes — the QStash poll, **Re-check now** and the callback — nor on DELETE. A build accepted while the gate was on publishes at gitpage whatever happens here, so settling it only keeps the doc truthful, and a gated-off workspace keeps its published site (see [feature gates](../architecture/feature-gates.md)). WS-3 must decide whether the hand-off, which does new work in the workspace, runs for a gated-off one.

**Not ported yet — the code carries a marked seam for each:**

- **WS-3, the publish hand-off** (`website-handoff-service.ts`): the "Website contact" form created before the submit, the `leadstack` wiring block, and on publish the chat allowlist, KB and persona seed, speed-to-lead workflow and push. Until then a published premium site has no form or chat widget wired in and `WebsiteDoc.provisioning` stays `null`. Also WS-3: storing the redirect-resolved live URL (`resolveLiveUrl`, which must go through the SSRF guard) — today `liveUrl` is the address gitpage reports — and resolving an apex → www redirect on the app URL before it is baked into the callback URL.
- **WS-4:** the post-publish PageSpeed check (`settleWebsiteBuild` does not schedule it), custom domains and the edit helper.
- **WS-5 / WS-6:** the premium form sections and the wizard. **WS-7:** the assistant's `list_website_concepts` and premium `create_website` arguments.

**Known items, left as they are.**

- **The callback's HMAC key is the gitpage API key.** That is gitpage's contract: there is no separate signing secret, so whoever holds the key that starts builds can also sign callbacks, and rotating one rotates both.
- **A removed member keeps gitpage editor access.** Every build invites the builder's email as an editor of the site on gitpage. Removing that person from the sub-account here does not remove them there; it has to be done on gitpage.
- **`verifyQStashSignature` is called without the URL argument** in the poll route (as in most QStash workers here, pre-existing), so a signed QStash message is not bound to the path it was sent to. The poll route does check the body's `subAccountId` and `siteId` against the path.

**Tests.** Unit and seam tests sit beside each file (`route.test.ts` for the callback, PATCH/reset, concepts and poll routes; `websites-service.transition.test.ts`, `websites-service.settle.test.ts`, `websites-service.build-v2.test.ts`, `client.premium.test.ts`). The poll seam tests interleave the writers on purpose: a callback, a reset or a rebuild lands while a tick is waiting on gitpage. [e2e/specs/website-build-settled.spec.ts](../../e2e/specs/website-build-settled.spec.ts) posts unsigned, mis-signed and signed callbacks to the real server and loads the website page. The E2E job generates a random `GITPAGE_API_KEY` for each run (masked, never derived from the run id, and not a gitpage credential), with `GITPAGE_API_URL` pointed at a closed loopback port.

## AI-driven website builds (Workspace Assistant action)

The Workspace Assistant (and the Agency Assistant via the `_in_sub_account` wrapper) can build a website from a chat request — "build me a gym website like fitness.com". Three registry entries in [src/lib/ai-suite/capabilities/](../../src/lib/ai-suite/capabilities/) (`website-research.ts`, `website-create.ts`, `website-status.ts`):

- **`research_website_reference`** (readonly, admin) — Firecrawl single-page scrape of a reference URL (accepts bare domains, prefixes https://), main content capped at 5,000 chars fed back to the model for tone/services/positioning. Degrades to a "draft from the description" note when `FIRECRAWL_API_KEY` is unset or the page can't be read — never throws at the user.
- **`create_website`** (confirm-gated write, admin) — the model drafts the full config: niche template pick (`gym_fitness` / `home_services` / `real_estate` / none), heading/hero (≤80), features/benefits (3 comma phrases ≤60), design fields as JSON-schema **enums lifted from `gitpage-values.ts`** so invalid values are unrepresentable, optional VSL (requires a video embed URL). Contact email + CTA link fall back to the workspace's saved `accountContact.email` / `bookingLink`; `business_name` falls back to the AI-agent profile's businessName, then the sub-account name — real data over model guesses, and a `CapabilityUserError` asks the user when no fallback exists. Niche/local contact pages require a real street address — validate() refuses and tells the model to ask rather than invent one. One confirm = create the site doc + submit the build. On a failed submit the just-created draft is deleted so it doesn't burn one of the 5 slots.
- **`check_website_status`** (readonly, any member) — lists the workspace's sites with status + live URL for "is my site done?".

Execution goes through [src/lib/server/websites-service.ts](../../src/lib/server/websites-service.ts) — `createWebsiteForSubAccount()` + `submitWebsiteBuildForSubAccount()`, extracted from the create/build routes (which now delegate). Every guard is shared: the `websiteEnabledByAgency` gate, the 5-site cap, `GITPAGE_API_KEY` presence, config normalization + validation, gitpage error mapping (incl. the 401 key-invalid heartbeat flip), and QStash poll scheduling. **No new env vars** — reuses `FIRECRAWL_API_KEY` (optional), `GITPAGE_API_KEY`, `QSTASH_*`.
