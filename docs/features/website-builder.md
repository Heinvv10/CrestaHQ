# Website builder (gitpage.site v1)

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

Each sub-account can hold **up to `MAX_WEBSITES_PER_SUBACCOUNT` (5)** website docs at `subAccounts/{id}/website/{siteId}` (see [src/lib/website/limits.ts](../../src/lib/website/limits.ts)). The legacy singleton at `.../website/main` remains valid as one of the slots — no migration. The page at [my-ghl-app/src/app/(dashboard)/sa/[subAccountId]/website/page.tsx](../../src/app/(dashboard)/sa/[subAccountId]/website/page.tsx) owns the collection `onSnapshot` + the "Add website" affordance + the account-wide activation gate, and renders one card per site via [src/components/website/website-builder.tsx](../../src/components/website/website-builder.tsx). Each `<WebsiteBuilder/>` is a compact status card; all input happens in the stepped build wizard it opens (see [The build wizard](#the-build-wizard-ws-6--not-runtime-verified)); the parent passes the live doc down (one listener, not one per card). Cap is enforced server-side in `POST /api/sub-accounts/[id]/website` (the create-site route, returns 409 on the 6th). Site cards expose a **Remove** (trash) action that deletes the doc to free a slot. There is no Rebuild on a live site.

- **Submit**: [src/lib/gitpage/client.ts](../../src/lib/gitpage/client.ts) `submitBuild()` POSTs to `https://www.gitpage.site/api/v1/generate-site` with `buildType: "local" | "vsl"` (selected by the user via the **Site type** picker on the page) and the agency's `GITPAGE_API_KEY`. Returns 202 + `formResponseId` (prefixed `build_…`). A 2xx without a `formResponseId`/`pollUrl` is not a build: the submit fails with a fixed-text 502 (gitpage's body is logged, not returned), the site keeps its status, and the hourly build reservation stays spent. The build route persists `status: "queued"` and the job id, then schedules the first QStash poll. v1 contract is frozen — additions ship into v1, breaking changes land at `/api/v2/`.
- **Build types**: `local` is the multi-page LocalSite (home + optional services/contact/terms). `vsl` is a single-page Video Sales Letter funnel — hero + embedded video + bullets + one CTA. The VSL form drops the Pages/Services/Business sections and shows a Video section instead; `video_link` (any http(s) embed URL — YouTube/Vimeo/Wistia) is required, and `cta_link` is mandatory because the funnel collapses without a destination after the video. Mode is stored on `WebsiteConfig.build_type`; existing docs without it default to `"local"` on read.
- **Polling**: [src/app/api/sub-accounts/[id]/website/[siteId]/poll/route.ts](../../src/app/api/sub-accounts/[id]/website/[siteId]/poll/route.ts) is a QStash signature-verified callback that hits gitpage's status endpoint every 20s (40s after five minutes), mirrors the result into Firestore, and reschedules itself until terminal (Published/failed) or the cap derived from gitpage's duration estimate (45 ticks for a job with no estimate, up to 120 — see [Premium builds](#premium-builds-website-build-v2--not-runtime-verified)). A terminal result is handed to `settleWebsiteBuild()`. The QStash payload carries `siteId` (verified against the path) so each site polls its own doc; dedup ids are namespaced by `siteId`. The route is in PUBLIC_PATH_PATTERNS in middleware (regex now `…/website/[^/]+/poll`) because security comes from the signature, not the session cookie.
- **Field name mapping**: internal types use snake_case (matches the rest of the codebase); the gitpage client transforms to camelCase + flat `pages` array at submit time.
- **Design fields**: dropdowns with gitpage's curated values (see [src/lib/website/gitpage-values.ts](../../src/lib/website/gitpage-values.ts)). gitpage silently falls back to defaults on unknown values, which would look broken — dropdowns prevent that.
- **Custom palette** requires a 3-hex triple in `customColors`; conditional input appears when `design_color_palette === "Custom"`.
- **Reset vs Remove**: `DELETE /api/sub-accounts/[id]/website/[siteId]?reset=1` resets the doc to `draft` (preserves config, clears jobId/liveUrl/status). Since WS-6 no button calls it (upstream 1.0.40 keeps the route branch the same way). `DELETE /api/sub-accounts/[id]/website/[siteId]` (no flag) permanently removes the doc to free a slot — the Remove button. Either way the previously-published GitHub repo stays live until manually deleted on gitpage's side — v1 doesn't tear down.
- **Auth model**: one `GITPAGE_API_KEY` per agency; shared across all sub-accounts. Each build's `subAccountId` is sent so gitpage tags the build record. Filter all reads/writes by sub-account on our side — gitpage scopes by agency, not sub-account.
- **Rate limit**: gitpage caps at 30 builds/hour/agency and returns 429 with `resetAt` when exceeded. On our side each sub-account gets `WEBSITE_BUILDS_PER_HOUR` (10) build submits an hour, counted before gitpage is called — see Build limits under [Premium builds](#premium-builds-website-build-v2--not-runtime-verified).
- **Heartbeat / subscription gate**: [src/lib/gitpage/heartbeat.ts](../../src/lib/gitpage/heartbeat.ts) `sendHeartbeat()` checks the deployment's website-builder subscription. The response includes `gitpageStatus.agency: boolean` which gets cached at `system/gitpageStatus`. The website-builder UI reads that doc via `onSnapshot` and renders an "activate" banner when `agency === false`. Fired once per cold start via [instrumentation.ts](../../instrumentation.ts) and once daily via QStash → [/api/cron/gitpage-heartbeat](../../src/app/api/cron/gitpage-heartbeat/route.ts) (signature-verified). To set up the daily schedule: in Upstash QStash dashboard create a schedule pointing at `${NEXT_PUBLIC_APP_URL}/api/cron/gitpage-heartbeat` with cron `0 3 * * *`.

## Premium builds (Website Build v2 — NOT runtime-verified)

**Status: ported from upstream 1.0.40, merged dark, never run against gitpage.** Production has no `GITPAGE_API_KEY` and `websiteEnabledByAgency` is off for every sub-account, so nothing below has built a real site. The first client to enable the builder triggers a live walk. The port is split into seven units (`UPSTREAM_PORT_PLAN.md`, P3); this section describes what is on `main` and names what is not.

Premium is gitpage's staged build: one of three authored design directions ("concepts") per niche, copy written from the operator's facts, generated photography. gitpage estimates 20 minutes (`estimatedDurationSeconds: 1200`).

**Shipped (units WS-1, WS-2 and WS-3):**

- **Every build is premium.** `normalizeWebsiteConfig` forces `quality: "premium"`, so a draft saved as `standard` builds as premium. The premium flags default on (`include_form`, `include_chat`, `include_voice`); a blank concept is stored as `null` and gitpage picks the niche default. The wizard (WS-6) sends the concept, hero motion, the story facts and the form/chat toggles.
- **Request** ([lib/gitpage/client.ts](../../src/lib/gitpage/client.ts)): premium adds `quality`, `claudeModel: "opus-5.5"` (`PREMIUM_CLAUDE_MODEL`, forced whatever the agency's gitpage dashboard says), a `premium` block (concept, `mode` from the colour scheme, `heroMotion`, and the typed facts parsed by [lib/website/premium.ts](../../src/lib/website/premium.ts)), optional `referenceNotes`, `editorEmail` (the builder's Firebase Auth email, lower-cased; gitpage invites it as an editor of the new site) and `callbackUrl`. The callback URL and the `leadstack` wiring block (`formSubmitUrl` for the sub-account's "Website contact" form, `widgetScriptUrl` for the chat widget) are built from `resolvedAppUrl()` ([lib/server/app-url.ts](../../src/lib/server/app-url.ts): `NEXT_PUBLIC_APP_URL` with an apex → www redirect followed, so nothing baked into a site redirects and fails CORS) and sent only when that is a bare `https://host` origin. The form is found or created by `ensureWebsiteContactForm` before gitpage is called — ONE per sub-account, reused across rebuilds and sites, claimed in a transaction in `private/websiteHandoff` so two simultaneous builds cannot make two. If it cannot be prepared the submit fails with 500 after the hourly reservation is taken; the reservation is not given back (see Build limits).
- **One guarded write.** Every write to a site doc's build state goes through `transitionWebsite(docRef, { expectJobId, fromStatuses, when }, patch)` in [websites-service.ts](../../src/lib/server/websites-service.ts): it re-reads the doc in a transaction and applies only if the doc still carries the job the writer acted for and is in a status that writer may move it from; otherwise it is a no-op and the writer stops (no reschedule, no hand-off). Five writers race on the doc — the poll tick, **Re-check now**, the callback, the draft save, and a build submit or reset — and each reads, then spends up to seconds on gitpage or QStash, then writes. So: `ready` is never written over, and never becomes `failed` (a 4xx, the cap timeout, a failed reschedule); an in-flight bump never lands on a settled doc; an old job's tick cannot touch the job that replaced it; a reset during a tick leaves a draft with no job, not `building` with none. Upstream uses plain updates throughout; this is a deliberate difference, because the WS-3 hand-off creates a workflow that messages leads and must run once.
- **Settle.** `settleWebsiteBuild()` is the ONE terminal handler, shared by the QStash poll tick, **Re-check now** and the callback. It writes `status`, `liveUrl` (gitpage's address with redirects resolved — see Hand-off), `statusPhase`, `conceptName`, `gitpagePageId`, `pollAttempts` and `settledDelivery` (`{jobId, status}`: the report it applied). It applies while the site is queued or building — or `failed` when the caller is the manual re-check, or when gitpage now reports Published after the poll cap gave up. A caller that loses returns `"noop"`. **Published with no live URL** (missing, empty, whitespace) is not settled: a site is never `ready` with no address, and the poll comes back for it. **Published at an address that is refused** (see Callback) settles as `failed`, with a message naming the address, and is logged — otherwise the site would poll to its cap and nobody would be told; a later report with a usable address still makes it ready. **A repeat of the report already applied** for that job is ignored while the site is still settled that way. `settledDelivery` is cleared whenever the site goes back in flight (the re-check's resume, a new build, a reset), so a resumed build that fails a second time is recorded as failed rather than mistaken for a repeat. That means the record does not protect a resumed build from a replayed failure report: the two are indistinguishable, and stranding a genuinely failed build in `building` is the worse outcome.
- **Callback.** `POST /api/webhooks/gitpage/build-settled` ([route](../../src/app/api/webhooks/gitpage/build-settled/route.ts)) is public (in `PUBLIC_PATH_PATTERNS`, exact path). Its only credential is `X-Gitpage-Signature: sha256=<hex>`, the HMAC-SHA256 of the RAW body under `GITPAGE_API_KEY`, compared in constant time before the body is parsed. The body is capped at 64 KB (Content-Length, then the bytes as read) BEFORE the HMAC is computed: 413 over it. A bad or missing signature is 401; no key on the deployment is 503; everything else is 200 (`settled` or `ignored: <reason>`) so gitpage never retries in a storm. The site is found by `gitpageJobId` inside the `subAccountId` the signed body names (which must be a document id, never a path). A signed body is still outside data: a `status` that is not a string reads as in flight; the live URL is trimmed, then kept only if it has no whitespace or control characters inside it, parses, is `https:`, carries no credentials, is not localhost or a non-public IP literal, and is at most 2,048 characters; error and stage text, the concept name and the partial-error list have every run of control characters (newlines included) collapsed to one space and are length-capped, and a page id that is over-long or carries control characters is dropped — these strings reach the site card and the assistant's `check_website_status` answer (`normalisePollBody` in the client, so the poll's answer is held to the same rules). The poll loop keeps running alongside it.
- **Polling.** The cap is `pollAttemptCapFor(estimatedDurationSeconds)`: 1.5× the estimate at the 20s cadence, clamped to 45–120 ticks (90 for a 20-minute premium estimate). `pollDelayFor` backs off from 20s to 40s once 15 ticks have run, so the wall clock the cap spans is longer than ticks × 20s: `pollWindowSecondsFor` gives 3,340 seconds (about 55 minutes) for a premium build's 90 ticks and about 25 minutes for the 45-tick floor. The timeout message quotes that figure. `WebsiteDoc.statusPhase` mirrors gitpage's stage on every in-flight tick. A tick whose write does not apply (see One guarded write) answers `stale-tick` and does not reschedule. **Re-check now** starts a poll chain in two cases only. It resumes a `failed` site that gitpage is still building (attempts reset, one chain). And on a site still queued or building it revives a chain that has died: the doc has not been written for two of the chain's intervals (`pollChainStaleAfterMs` — 40s early on, 80s after the backoff; a live chain writes the doc every tick). The revive checks that and writes `updatedAt` in one guarded transition, so of any number of clicks only the first finds the doc stale; the attempt count is kept, so the cap still applies. On a live chain the click refreshes the stage only and leaves `updatedAt` alone (it is the chain's heartbeat). Repeated clicks therefore cannot multiply chains or push the cap out, and a card whose chain died is not left spinning — in-flight cards offer neither Rebuild nor Remove. A chain that is alive but more than two intervals late gets a second chain beside it; both stop at the same terminal state or cap.
- **Draft save.** `PATCH /api/sub-accounts/[id]/website/[siteId]` (`{config, wizardStep}`, sub-account admin) stores a partial config and the wizard step to resume on. It is refused with 409 while the site is queued or building, and while it is `failed` but still carries its job id — a re-check or a late callback can still make that build the live site, and the stored config must be the one it was built from. The check and the write are one transaction. It never touches status, job id or live URL. Gated: 403 when `websiteEnabledByAgency` is off. The wizard calls it on every Next and on close. **Difference from upstream:** upstream's wizard saves the draft when a failed build is reopened with Try again. Ours sends no save while the site is `failed` with a job id, because this route would refuse it. The review step then says the changes are kept only if the operator builds again (the build route accepts that site and replaces the job).
- **Build limits.** `submitWebsiteBuildForSubAccount` answers 409 for a site that is already queued or building (checked before gitpage is called, and again atomically with the write), 409 for a build on a new site id once the sub-account is at `MAX_WEBSITES_PER_SUBACCOUNT`, and 429 with `Retry-After` past `WEBSITE_BUILDS_PER_HOUR` (10) submits per sub-account per hour — gitpage's own cap of 30 an hour is per agency, so one workspace could otherwise use every other workspace's builds. Both limits are atomic and hold across instances, through `subAccounts/{id}/private/websiteLimits` ([collections](../architecture/firestore-collections.md)): the hourly counter is reserved in a transaction BEFORE gitpage is called, and a reservation is consumed whatever happens after it is taken — gitpage accepting, gitpage answering 4xx or 5xx, or the request throwing (a network error, a timeout). There is deliberately no release: a throw does not prove gitpage was not reached (a timeout, or an answer lost after the request was sent, leaves a build possibly accepted), so giving reservations back would let anyone who can make requests fail that way start builds without limit. **The consequence: ten failed attempts within the hour — including ten made during a gitpage outage — lock builds for that workspace until the window rolls** (at most an hour from the first of them; the 429 carries `Retry-After`). Nothing shortens it but the clock; an operator who must build sooner has to clear `private/websiteLimits` by hand. A count that is not a whole number ≥ 0 inside an open window reads as the limit reached (fails closed); every creation of a site doc — **Add website** and a build on a never-created id alike — counts the sites and creates in one transaction that also writes that doc, so concurrent creations conflict and cannot pass the cap together. The cap is counted where the doc is written: the sub-account comes from the doc's own path, the path must be exactly `subAccounts/{id}/website/{siteId}`, and the build and **Add website** refuse (404) a sub-account id that is not a document id, as the build does a `siteId` — a site id that is really a path (`x/y/z`) would otherwise create a doc in a nested collection the count never sees. The draft save, reset, Remove and **Re-check now** answer 404 for such a `siteId` before anything touches Firestore (an id that makes the doc path an even number of segments is not a document path, and the Admin SDK would throw: a 500). A reservation or creation that loses to contention after its retries is refused with 429 (fails closed). **The counter is the real bound on calls to gitpage.** The in-flight 409 is a courtesy: a reset (`DELETE …?reset=1`) clears the in-flight state, and two submits for one site in the same instant both pass the early check. In the second case both reach gitpage, one takes the site, and the other gets 409 with its gitpage build orphaned (logged with the job id) — as does a build whose site was removed while gitpage was being called (the site stays removed; a submit creates a doc only when it read the site as absent itself, and a created doc always carries its tenancy keys). Each of those spent one of the ten.
- **Hand-off** ([website-handoff-service.ts](../../src/lib/server/website-handoff-service.ts)). When a premium build settles as `ready`, the caller that won the settle claim — and only that caller — registers `provisionWebsiteHandoff` with `runAfterResponse` (every settle caller is a request: the poll tick, **Re-check now**, the callback). Each step is best-effort and independent; a failure is recorded in `WebsiteDoc.provisioning.errors` and the others still run, and a hand-off that throws is recorded the same way. The summary is written through `transitionWebsite` for the same job while the site is still `ready`, and the patch is only `provisioning` + `updatedAt`, so the hand-off can never un-settle or re-settle a site; a summary for a site that was reset, rebuilt or removed meanwhile is dropped. Every write step re-reads the site and the sub-account in its own transaction: if the site was removed, rebuilt (another job) or is no longer `ready`, or the website gate went off, the hand-off stops there, writes nothing more and records `hand-off stopped: <reason>` (a speed-to-lead draft it had just created is deleted). That record is the summary written to the site doc's `provisioning` — so a workspace whose gate is switched off mid-hand-off still gets a summary saying the hand-off stopped (its site is still `ready` for the same job); a site that was removed or rebuilt gets none, because the summary write is guarded on the job too. Steps: (1) the live hostname — and ONLY it — is appended to `webChat.allowedDomains`, the 25-entry cap checked and the entry appended in one transaction (a full list is reported, not overflowed), and gitpage's welcome message and accent fill those fields only where they are blank, stock or still the value the last hand-off seeded — that record is `websiteSeeded` on the web-chat channel doc itself, written in the same transaction as the values, so a later failed profile write cannot leave the widget's seeds unrecorded. **Deliberate difference from upstream:** gitpage's reported path-URL host (`namespace.gitlab.io`) is never allow-listed, because GitLab serves every project in that namespace — other tenants' sites included — from that one origin. Nothing is allow-listed when the redirect walk did not land on a site (`chatSkippedReason` says so), or when the host it landed on is the reported host and that host is shared: the report was under a path, or it is a `gitlab.io` / `github.io` host (the namespace root reported as-is, or a path URL that redirects back to `/`). A different host the walk landed on is the site's own and is allow-listed whatever path it ended on (`/index.html`, `/en/`). If gitpage ever reports the unique `*.gitlab.io` domain directly (no redirect), it cannot be told apart from a namespace root, so nothing is allow-listed — this fails closed, and `chatSkippedReason` says why. A reported host that is itself a public suffix (`co.za`, `netlify.app`) has no redirect family and is never allow-listed. A hostname is never an IP literal; (2) the KB (`websiteKb`, `websiteKbSource: "gitpage-build"`, `websiteKbSiteId`) and persona (`websiteUrl`, `systemPrompt`, `businessName`, escalation keywords on a new profile only, `escalationNotifyEmail` from the contact details) are seeded on the same terms, in one profile write, with `websiteSeeded` recording what was filled in automatically — an operator's own `websiteUrl` is kept (upstream overwrites it on every publish); (3) ONE speed-to-lead workflow per sub-account, triggered by the site's form, from the `speed-to-lead` seed, with the SMS step kept only if the sub-account's own Twilio or the shared one (when the agency allows it) is configured and the email step only if `emailIsConfigured(sub)` (its own verified SMTP, else the Resend env); (4) a push to the team. **Deliberate differences from upstream:** the workflow is always created as a DRAFT and never published or activated, and the web-chat bot is never switched on — nothing automated starts messaging leads; `provisioning.workflowId` / `workflowStatus: "draft"` and `chatSkippedReason` say what is waiting for a person. That covers only what the hand-off creates. A website form submission fires `form.submitted` like any form, so an operator's own ACTIVE `form.submitted` workflow with no `formId` filter (an "any form" workflow) enrols website leads as soon as the site is live — existing engine behaviour, not something the hand-off switches on or off. Every gitpage value is outside data: the accent must be `#RRGGBB` (stored lower-cased), the welcome message and business name are control-character-stripped onto one line and capped (400 / 200), the KB and prompt keep line breaks but lose other control characters and are capped (6,000 / 8,000), and hostnames come only from an address that passes `safePagesUrl` and is a plain DNS name. No Web Voice step (unit WV-5).
- **Live URL.** `resolveLiveUrl` follows the address gitpage reports (GitLab's path URL 308s to the project's unique domain, the host visitors load) with a manual redirect walk: one `publicFetch` HEAD per hop (production connects only to public addresses and never follows a redirect itself), each `Location` resolved against the hop it came from and required to be a plain public https site address in the reported host's family before it is requested: for a `gitlab.io` / `github.io` report, any host under that Pages parent (where the project's unique domain lives); for any other host, only itself, its subdomains and its www/apex twin, decided on the registrable domain from the Public Suffix List (`acme.co.za` never reaches `evil.co.za`; a trailing dot is stripped first, so `acme.com.` does not widen to all of `.com`), at most five requests, ONE 3 s deadline across all of them, a 64 KB body cap. It never throws: on the hop cap, a redirect with no `Location`, a refused hop, a timeout or any error it returns the reported address marked unresolved, and the hand-off then allow-lists nothing. A landing on GitLab's sign-in or Pages access-control host is refused too. It runs before the settle claim, so a site is never `ready` at one address and then moved to another.
- **Refresh chat knowledge from a site.** `POST /api/sub-accounts/[id]/ai-agent/profile/refresh-kb` with `{ siteId }` re-scrapes that site's home page and its selected Services and Contact pages through Firecrawl into the KB, labelled per page (`websiteKbSource: "firecrawl"`, `websiteKbSiteId`). Besides the route's AI-channel gate it answers 403 when `websiteEnabledByAgency` is off (upstream checks only the AI gate), 404 for a `siteId` that is not a document id (before any read) or a site of another sub-account, and 400 for a site that is not `ready`. Without `{ siteId }` it behaves as before. The Edit site window's "Update chat bot" sends the `siteId` (WS-6 wires that window into the card).
- **Concepts.** `GET /api/sub-accounts/[id]/website/concepts?niche=…` is a member-authed proxy over gitpage's `GET /api/v1/concepts`; the agency key never reaches the browser. Gated: 403 when `websiteEnabledByAgency` is off. Every error body carries a stable `code` (`unauthorized`, `forbidden`, `not_found`, `gate_off`, `internal`, `not_configured`, `bad_niche`, `upstream`) and the picker maps on it, not on the status. Any gitpage failure — 4xx included, so a revoked key is never mistaken for an expired session — is our 502 `upstream` with fixed text; gitpage's message is logged, never forwarded. The picker (`ConceptPicker` in `website-premium-sections.tsx`) clears a saved concept only when a *successful* list lacks it; a failed load leaves it alone.

**The agency gate.** `websiteEnabledByAgency` stops new work: create, build, the draft save, the concepts proxy and the custom-domain save all answer 403 with the same message (upstream gates only create and build). It is deliberately not checked where a build finishes — the QStash poll, **Re-check now** and the callback — nor on DELETE of a site or its custom domain. A build accepted while the gate was on publishes at gitpage whatever happens here, so settling it only keeps the doc truthful, and a gated-off workspace keeps its published site (see [feature gates](../architecture/feature-gates.md)). The hand-off is different: it does new work in the workspace, so a gated-off workspace gets none — its site is settled and nothing more (the gate is read when the build settles, not when it was accepted; missing or not literally `true` is off).

**Shipped (unit WS-4, after publish) — also NOT runtime-verified:**

- **Custom domain.** `PUT /api/sub-accounts/[id]/website/[siteId]/domain` `{domain}` ([route](../../src/app/api/sub-accounts/[id]/website/[siteId]/domain/route.ts)), sub-account admin, gated (403), on a `ready` site only (409): stores the bare hostname on `WebsiteDoc.customDomain` and adds it **and its www/apex twin** to THIS sub-account's Web Chat `allowedDomains`. The apex is the registrable domain from the Public Suffix List (`lib/prospecting/registrable-domain.ts`), so `peakyoga.co.za` pairs with `www.peakyoga.co.za`; any other subdomain (`shop.peakyoga.co.za`, `www.shop.…`) adds just itself. Both ids in the path must be document ids, and the site must live under the sub-account in the path and carry its id. Refused (400): anything that is not a plain hostname (no wildcard, IP, port or single label), `localhost` and any `*.localhost` host, a bare public suffix (`co.za`, `gitlab.io`), a `gitlab.io`/`github.io` host, and this app's own host or any host under it (Labs funnel subdomains are other tenants' pages) — and every domain when `NEXT_PUBLIC_APP_URL` is unset, since the app host is then unknown. Refused (409): a domain whose hosts another site of the same sub-account holds, so removing one site's domain can never take off hosts another still relies on. **The site doc and the allow-list are written in ONE transaction** (`transitionWebsite` with its `inTransaction` step; the allow-list is read and written through `webChatAllowListInTx` in `lib/comms/ai/agent.ts`), which re-reads the site, the sub-account's other sites and the list, counts the 25-entry cap (409 past it), and writes both or neither — so a DELETE, another site's save or a Web Chat settings save landing at the same moment cannot leave a host allowed without a record, a record without its hosts, or a lost edit. The site records the hosts the save added (`WebsiteDoc.customDomainChatHosts`: its pair minus any already listed); replacing or removing the domain takes those off and nothing else, so hosts the operator listed by hand stay. The chat bot's `websiteUrl` moves to the domain only when it pointed at this site — in the same transaction, so it never names a domain that a concurrent DELETE has removed. `DELETE` (admin, NOT gated, like removing a site — a domain can always be taken back) clears the domain, removes its recorded hosts (the list is not rewritten when none of them is on it) and points the chat bot back at the live URL if it was on the domain, all in the same single transaction. **Removing the whole site** (`DELETE …/website/[siteId]`, not a reset) takes its recorded hosts off the allow-list, and points a chat bot that was on its domain back at the live URL, in the same transaction as the delete — once the doc is gone nothing would record them; a reset keeps the domain and its hosts. The domain belongs to the site, not to a build: unlike the build-state writes, the domain save is not tied to the job id, only to the site being `ready`. By design, a recorded host the operator removes by hand and later re-adds by hand is still taken off by DELETE (the record cannot tell the two apart). **Web Chat's test mode:** an empty allow-list lets the widget run on localhost and this app's own host (previews). The first domain save ends that — only listed hosts are allowed from then on, so add a preview host by hand to keep testing there — and a DELETE that takes the last host off the list puts the widget back into test mode.
- **UI.** `WebsiteDomainDialog`, `WebsiteEditHelper` (the GitPage-MCP edit prompt; its "Update chat bot" posts `{siteId}` to `refresh-kb`, which WS-3 teaches to read a site) and `WebsiteSeoPanel` (a Search Console reminder) are ported verbatim from upstream. A `ready` site's card opens them: **Add custom domain** / **Domain settings**, **Edit site**, and the Search Console line below the card (WS-6). NOT browser-verified.
- **PageSpeed check not ported — upstream stores scores nothing displays.** Upstream queues a QStash call per publish to a public `…/website/[siteId]/pagespeed` route that writes `WebsiteDoc.pagespeed`; nothing reads that field, upstream included. The field stays on the type (WS-1); nothing writes it.

### The build wizard (WS-6 — NOT runtime-verified)

Ported from upstream 1.0.40 ([website-wizard.tsx](../../src/components/website/website-wizard.tsx), verbatim apart from the marked changes), with the card rewrite in [website-builder.tsx](../../src/components/website/website-builder.tsx). **NOT browser-verified**, and never run against gitpage (see the status note above).

- **Steps.** `wizardStepsFor(config)` derives them from the choices so far: Start (site type, niche), The business, Pages & services (a VSL gets Video instead), Location & hours (only when the contact page is on), Look & feel (concept, hero, colours), Your story (premium only, optional), Review & build. **Known items, left as they are.**

- **The callback's HMAC key is the gitpage API key.** That is gitpage's contract: there is no separate signing secret, so whoever holds the key that starts builds can also sign callbacks, and rotating one rotates both.
- **A removed member keeps gitpage editor access.** Every build invites the builder's email as an editor of the site on gitpage. Removing that person from the sub-account here does not remove them there; it has to be done on gitpage.
- **`verifyQStashSignature` is called without the URL argument** in the poll route (as in most QStash workers here, pre-existing), so a signed QStash message is not bound to the path it was sent to. The poll route does check the body's `subAccountId` and `siteId` against the path.

## AI-driven website builds (Workspace Assistant action)

The Workspace Assistant (and the Agency Assistant via the `_in_sub_account` wrapper) can build a website from a chat request — "build me a gym website like fitness.com". Four registry entries in [src/lib/ai-suite/capabilities/](../../src/lib/ai-suite/capabilities/) (`website-research.ts`, `website-create.ts`, `website-status.ts`, `website-cta.ts`):

- **`research_website_reference`** (readonly, admin) — Firecrawl single-page scrape of a reference URL (accepts bare domains, prefixes https://), main content capped at 5,000 chars fed back to the model for tone/services/positioning. Degrades to a "draft from the description" note when `FIRECRAWL_API_KEY` is unset or the page can't be read — never throws at the user.
- **`create_website`** (confirm-gated write, admin) — the model drafts the full config: niche template pick (`gym_fitness` / `home_services` / `real_estate` / none), heading/hero (≤80), features/benefits (3 comma phrases ≤60), design fields as JSON-schema **enums lifted from `gitpage-values.ts`** so invalid values are unrepresentable, optional VSL (requires a video embed URL). Contact email + CTA link fall back to the workspace's saved `accountContact.email` / `bookingLink`; `business_name` falls back to the AI-agent profile's businessName, then the sub-account name — real data over model guesses, and a `CapabilityUserError` asks the user when no fallback exists. Niche/local contact pages require a real street address — validate() refuses and tells the model to ask rather than invent one. One confirm = create the site doc + submit the build. On a failed submit the just-created draft is deleted so it doesn't burn one of the 5 slots.
- **`check_website_status`** (readonly, any member) — lists the workspace's sites with status, live URL, call-to-action link and site id for "is my site done?" (and to resolve the id before `update_website_cta`); a failed site that still has a gitpage job is flagged as not re-pointable until Re-check now or Try again on the Website page.
- **`update_website_cta`** (confirm-gated write, admin, **chat-only** — not on the Agent API, since it republishes a public site and spends a paid build; STL-2) — sets `config.cta_link` and rebuilds through `updateWebsiteCtaAndRebuild()`, which hands the stored config to `submitWebsiteBuildForSubAccount()` with `requireExisting: true`, so the gate, key, validation, the in-flight refusal, the hourly build counter and `transitionWebsite` all apply unchanged, and a site removed meanwhile is refused rather than re-created. With `ctaOnly` it writes back only `config.cta_link` (a wizard save that lands while gitpage is called is kept) and, like the wizard's draft save, refuses a failed site whose last build can still finish (`hasUnsettledFailure`), before the build and again inside the write. The link must pass `safePagesUrl` (https, public host, no credentials, ≤2,048 chars); the card's site name must match the id's site (`siteDisplayName`, the name every assistant lookup prints: one line, at most 200 UTF-16 units, nothing `hasUnsafeText` refuses, and unchanged when sent back); a live site already carrying the link is not rebuilt. The Speed-to-Lead playbook calls it only after the user agrees in text.

Execution goes through [src/lib/server/websites-service.ts](../../src/lib/server/websites-service.ts) — `createWebsiteForSubAccount()` + `submitWebsiteBuildForSubAccount()`, extracted from the create/build routes (which now delegate). Every guard is shared: the `websiteEnabledByAgency` gate, the 5-site cap, `GITPAGE_API_KEY` presence, config normalization + validation, gitpage error mapping (incl. the 401 key-invalid heartbeat flip), and QStash poll scheduling. **No new env vars** — reuses `FIRECRAWL_API_KEY` (optional), `GITPAGE_API_KEY`, `QSTASH_*`.
