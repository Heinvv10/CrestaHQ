# Products + Invoices (v1, extends Quotes)

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

A reusable product catalog plus an Invoice document type that shares the Quotes collection. Built on top of v1 Quotes; same Firestore doc family, same builder, same public view — extended in three ways:

1. **`kind: "quote" | "invoice"` on the quotes doc.** A document starts life as either, or an accepted quote is converted to an invoice in place via `POST /api/sub-accounts/[id]/quotes/[quoteId]/convert-to-invoice` (kind flips, `INV-YYYY-NNNN` number issued, public token rotated). State machines diverge: quotes go `draft → sent → viewed → accepted → paid`; invoices go `draft → sent → viewed → paid` (no accepted step — operator confirms payment landed in Stripe and clicks Mark as paid).

2. **`products/{id}` collection.** Per-sub-account catalog: `name`, `description`, `unitPriceCents`, `currency`, `active`. The builder's "Add from catalog" picker snapshots `{name, description, unitPriceCents}` into the line item — editing/archiving a product later never mutates historical docs (the snapshot is authoritative; `lineItem.productId` is a back-reference). Routes: `GET|POST /api/sub-accounts/[id]/products`, `PATCH|DELETE /api/sub-accounts/[id]/products/[productId]`.

3. **Per-sub-account PayPal.me payment links (v1) / own-Stripe card rail (Payments v1, in progress).**

> **Superseded in part by Payments v1** (`PAYMENTS_V1_PLAN.md`). The card rail is
> **Tier 1: the sub-account pastes its own Stripe RESTRICTED key** — NOT Stripe
> Connect. Connect would make every buyer a Stripe *platform* (each deployment
> has its own `STRIPE_SECRET_KEY`), requiring a Connect platform profile + Stripe
> review per buyer and KYC per client. Tier 1 avoids all of that; Connect stays
> available later behind one branch in `getSubAccountStripe()`. **Payments v1 is
> further along than this note used to say** (corrected 2026-09-04): the
> connection, hosted checkout pages, order bumps, the `orders` collection, the
> per-sub-account webhook at `/api/webhooks/stripe/sa/[subAccountId]` and the
> `order-reconciler` are all built, and an invoice paid by card is marked paid
> automatically through the same `markQuotePaidServerSide` the manual button
> uses — there is no second paid-path. PayPal.me remains the only manual rail,
> because paypal.me has no payment callback. The paragraph below still
> describes the shipped PayPal path, which is untouched. Each sub-account pastes a PayPal.me username under `/sa/[id]/dashboard/settings` → **Payments — PayPal**; no API keys, no encryption layer, no platform credentials. On invoice send, `/api/sub-accounts/[id]/quotes/[quoteId]/send` generates `https://paypal.me/{username}/{amount}{currency}` from the invoice total and caches it on the doc as `paymentLinkUrl`. The recipient sees a **Pay** button on the public invoice page that opens the PayPal-hosted page with the amount pre-filled. paypal.me URLs are stateless — every send regenerates the URL (no API call, no "old link" to deactivate). Operator marks invoices paid manually after the payment lands in their PayPal account. The card upgrade is **Payments v1** above (own-Stripe restricted key, webhook-driven auto-mark-paid) — the Settings page's **Payments — Stripe** card is now that real connect flow, gated on `paymentsEnabledByAgency`.

**Orders needing attention.** When a card payment arrives but cannot settle what it paid for (invoice already paid, total changed, booking no longer waiting), the reconciler writes `order.attention` and sets `attentionOpen: true`. Reports → Payments lists open ones at the top for sub-account admins and the agency owner (collaborators don't see it), with **Mark resolved** (`GET/POST /api/sub-accounts/[id]/order-attention`), which sets `attentionOpen: false` + `attentionResolvedAt/ByUid/ByEmail` on the order; the orders table then shows the note as resolved. One flag per order + source, whatever the note's wording, so a redelivery neither re-emails nor reopens it. The sub-account's admins get one email per flag. Orders flagged before this shipped have no `attentionOpen` and are not listed. Details: [client-billing.md → Flagged payments](client-billing.md#flagged-payments-attention).

## Sell online (upstream 1.0.54 F1 model + editor, F2 buy pages on Stripe — NOT runtime-verified)

A product can be put on sale with its own buy link (`/co/[sa]/buy/[slug]`). F1 shipped the data model, the server validation and the editor; F2 the public pages and the Stripe payment path, F3 the Paystack path, F4 the delivery (below). Gated by `sellOnlineEnabledByAgency` (default off, [feature-gates.md](../architecture/feature-gates.md)); while off the Products dialog shows no Sell online block and the request is unchanged. NOT runtime-verified: no tenant has the gate on and no buy link has taken a real payment.

- **Fields** (optional on `products/{id}`, absent = catalog-only): `sellOnline`, `slug`, `publicDescription`, `checkoutPageId` (a published checkout page selling this product, for the Buy button), `delivery` (`none` / `community` group+course / `download` link), `publicVersion` (bumped on public-facing edits and archive).
- **Validation** (`lib/server/products-sell-online-service.ts`, used by `POST …/products`, `PATCH …/products/[productId]` and the agent `update_product`):
  - A sell-online key present with the wrong type (`sellOnline: "true"`, a non-string `slug`/`publicDescription`, a `checkoutPageId` that is neither a string nor null, a non-object `delivery`) answers 400; nothing is written.
  - Gate off: changing any sell-online field answers 403 `{ code: "gate_off" }`, except taking a product off sale (`sellOnline: false` alone), which is always allowed. Unchanged values round-tripped by the UI are a no-op 200.
  - Slug: lowercase kebab, 2–60 characters, not `api`/`new`/`thanks`/`preview`/`buy`; 409 when another product **or a checkout page** in the same sub-account uses it. Minted from the name on first sale, skipping both. Uniqueness is a query, not a claim doc (ruled 2026-10-30), so two simultaneous saves can still collide: **F2's slug lookup must fail closed — more than one product with the slug in the sub-account answers 404.**
  - While a product is (or becomes) for sale: price a whole number of cents, at least Stripe's minimum charge for the currency (`minSellOnlinePriceCents`, from Stripe's documented table: 0.50 in USD/AUD/EUR/CAD/NZD/CHF/SGD/ZAR, 0.30 GBP, 4.00 HKD, ¥50; 1.00 for a currency not in the table — a charge settled in another currency must also clear that currency's minimum after conversion, which isn't checked) and at most 100,000,000 (a whole unit in a zero-decimal currency such as JPY — Stripe charges those in whole units, so ¥123.45 would be charged as ¥123; a product already on sale at such a price fails closed — its buy page 404s and it leaves the catalog — until its price is fixed); currency one of `SELL_ONLINE_CURRENCIES` (the quote builder's list, incl. ZAR). Catalog-only products keep the old rules (price 0 allowed, any currency).
  - Turning it on, or changing an on-sale product's currency, needs a rail: `chooseProductPayRail(sub, currency)` (`lib/products/pay-rail.ts`, pure, also used by the editor). Stripe when Payments is on, `stripeConnectionMeta.ready` and Stripe can price the currency; else Paystack when Payments is on, a connection exists and the currency is ZAR. Both ready → Stripe (same order as invoices). Refusal: 400 `{ code: "no_pay_rail" }` with the reason.
  - Download links: public https only (no IP literal, localhost, userinfo or quote characters). Community/course and checkout page ids pass `isDocId`; the group must exist with Community on, the checkout page must be published and sell this product.
  - The PATCH validates and writes in one transaction against the product as it is at commit.
- **Hard delete** (`DELETE …/products/[productId]?hard=true`) of a product on sale answers 409 `{ code: "on_sale" }` ("take it off sale first"), re-checked in the delete's transaction. Archiving (the default delete) still works.
- **Agent tools:** a product on sale counts as sold (`productSellers` adds its buy link from the caller's own read of the product, inside the transaction for the re-checks), so the agent's `update_product` needs a person's "spend" approval for any edit of it (price and currency included), and `delete_product` is refused while it is on sale.
- **Snapshots** copy products catalog-only: the sell-online fields stay behind.
- **Checkout pages** created from a product skip reserved slugs.
- `listSellableProducts` (`lib/server/products-catalog-service.ts`) is the public catalog builder for F2/F6: on sale, valid price, and a rail for the currency right now.

### Buy pages and the Stripe path (F2)

F1 checks a product only when it is saved, and the world moves after it, so every public surface re-checks it from the stored docs (`loadBuyContext`, `lib/server/product-buy-service.ts`), at render AND at session creation:
- the sub-account id passes `isDocId` before any read; the slug is product-slug shaped;
- the agency gate, Payments and a rail for the currency right now (`chooseProductPayRail`), and email sending configured (`emailIsConfigured(sub)`, for F3's confirmation);
- exactly one product with the slug in the sub-account — more than one fails closed (404), since uniqueness is a query, not a claim doc;
- the product is `active`, `sellOnline`, in this sub-account, and its price passes `sellOnlinePriceError`;
- a `community` delivery's group (and course) still exists with Community on (`checkDeliveryTargets`, the save-time check);
- a `checkoutPageId` is followed only while that page is published and sells this product (`checkCheckoutPage`); otherwise the express page sells it.

**Pages** (all `noindex`; `/co` is already a middleware public prefix):
- `/co/[sa]/buy` — the catalog: `listSellableProducts`, minus a slug two products share; 404 with the gate off. A **published** checkout page slugged `buy` from before S1 reserved the slug renders here instead (a draft never hides the catalog) (this static folder shadows `/co/[sa]/[slug]`), and `/co/[sa]/buy/thanks` is its thank-you page. New checkout pages can't take `buy` (`checkoutSlugError`).
- `/co/[sa]/buy/[slug]` — 404 for anything not for sale; redirects to the linked checkout page when that page owns the sale. On the Paystack rail the page also asks for the buyer's email (Paystack's hosted page shows it but cannot ask for it). The button creates the session on click, never on load.
- `/co/[sa]/buy/[slug]/thanks?order=…&t=…` — shows the order only to the holder of its thanks token (random 32 bytes; only its SHA-256 is stored, as `orders.thanksTokenHash`, compared in constant time). What it says comes from the ORDER DOC, never the URL (`thanksView`, `lib/products/thanks-view.ts`): pending → "processing" (also when merely flagged, e.g. a Paystack key change on an abandoned buy: nothing says money arrived); held (`heldAt`: money arrived but did not match) or paid-and-flagged (`attention`/`attentionOpen`, see Reconcile) → "a quick check", no download; `expired` → "checkout expired, nothing charged" (but "a quick check" if it is flagged, i.e. a payment landed after all); refunded/failed → "no longer active"; paid or `partially_refunded` (with a "part refunded" note) → item, amount and the download link from the order's own `deliveries` snapshot (re-checked as public https at the sink). It says a confirmation email is on its way only when the workspace can send email and the send hasn't failed. Wrong, missing or foreign token → a generic thank-you with nothing about any order. `Referrer-Policy: no-referrer`, `noindex`.

**Session** (`POST /api/co/[sa]/buy/[slug]/session`, money half in `lib/server/product-buy-session.ts`): the per-IP checkout rate limit (shared with checkout pages) → body capped at 4 KB; only `requestId` read (a UUID, else 400), plus `email` on the Paystack rail → `loadBuyContext` (404) → linked checkout page (409) → `canBuyExpressNow` (503, no order, no session) → Stripe connection pre-check (503) → double-click dedupe → **pending order written first** (`source: "product_link"`, amount and currency from the product doc, `productLinkProductId`, `deliveries`, `thanksTokenHash`, empty `stripeCheckoutSessionId`) → Stripe Checkout Session (`centsToStripeAmount`, `leadstackOrderId` in metadata, success URL = the thanks page with the token) → `attachCheckoutSession` puts the session id on the order in a transaction (pending + no session only) → the URL goes to the browser. Any failure after the order is written (session call, no URL, attach) marks the order `failed`, so it can never be paid.
- **Dedupe:** the buy button mints a random `requestId` (UUID) once per page load and sends it. The same id for the same product within 30 s (a double click, or back from Stripe and click again) gets the session already opened for it — only while its order is still pending, linked, unheld and unflagged, and only while the product's price and currency are still what that session charges. No id → no dedupe; two ids never share a session (no IP is involved, so buyers behind one NAT never get each other's checkout). In-memory per process (like the rate limiter), keyed by an HMAC under a per-process random salt; a restart between two clicks only costs a duplicate pending order.

**Reconcile** (`lib/stripe/order-reconciler.ts` hands `product_link` orders to `handleProductLinkCompleted` in `lib/stripe/product-link-reconcile.ts`):
- **Paid only from pending, only on a match** (`settleProductLinkPayment`, one transaction — this source never goes through the generic `markOrderPaid`). A session that collected a different amount or currency **holds** the order: it stays `pending` with `heldAt` set, the payment intent and buyer recorded (so a refund still finds it), and it is flagged (`attention`, `attentionOpen`). A held order is never paid by any later event (a replay, a matching event, after a partial refund), is never delivered, emailed or expired, and never counts as revenue (`countsAsRevenue` in the payments report). **There is no release path in v1 (accepted):** resolving the flag (Reports → Payments → Mark resolved) only closes the alert — the order stays held, undelivered and out of revenue; the operator refunds it in Stripe or follows up with the buyer by hand. A manual "mark paid" may come later. Money for an order already `expired`, `failed` or `refunded` is flagged, never dropped: the first such payment is recorded on the order (payment intent and buyer, status unchanged) so a refund finds it, and a replay of a recorded payment is not flagged again.
- **Contact** (after paid, never blocking it). A paid order with no contact finds or creates the buyer's contact from Stripe's email (lower-cased, capped at 254; name at 200), email-first, and is linked once (`linkOrderContact`). The step is claimed first (`claimContactLink`: `contactLinkClaimedAt` + token, a 60 s lease), so concurrent deliveries create one contact: the others answer 5xx while the claim is fresh and take over once it is stale; a failing holder releases it. A failure throws, so the route answers 5xx and Stripe's redelivery retries until linked (idempotent: the email match finds a contact an earlier attempt created). **`order.paid` events** (webhook, workflow, activity) are claimed once (`orders.paidEventsFiredAt`) after that step, so the workflow sees the contact. They are **at most once**: an emit that fails after the claim is not retried. A persistent contact failure delays them until a delivery links it (Stripe retries for about three days), and an order fully refunded before its contact links never fires them (accepted). **Accepted (breaker REPRO 3):** the match is email-first, the same rule as forms, so a buyer who types an existing customer's email is recorded against that customer.
- **Confirmation email** (`lib/server/order-confirmation-service.ts`, upstream F3, pulled forward): after a `product_link` order is paid, a plain-text confirmation (item, amount, reference, download link or "we'll be in touch") goes to the buyer through `sendEmail` (the workspace's SMTP or the shared sender, metered, suppression-checked). Exactly once: `orders.confirmationEmail` is claimed (`sending`) in a transaction that requires `paid`, unheld, unflagged and unclaimed, then recorded `sent`/`failed` (with a contact activity). It echoes nothing the buyer typed (no name greeting, no email address): only the item names and amounts from our own order doc. Neither a `failed` nor a stuck `sending` claim (the process died mid-send) is retried — a buyer is never emailed twice, at the cost of a lost email in that case.
- **`checkout.session.expired`** marks a pending, unheld, unflagged `product_link` order `expired` (terminal: never paid afterwards; money that arrives anyway is flagged). Added to `SUB_ACCOUNT_WEBHOOK_EVENTS`; Stripe endpoints registered before this don't send it, so their unpaid buy-link orders stay `pending`.

**Paystack path (F3)** — a ZAR product on a workspace whose rail is Paystack (`chooseProductPayRail`; Stripe wins when both can take it). `POST …/session` also requires `email` (valid, at most 254 characters, else 400; nothing written) and hands off to `openProductPaystackSession` (`lib/server/product-buy-paystack.ts`):
- **Order, then attempt, then Paystack.** The pending order is written first (amount and currency from the product doc, `buyerEmail` from the form). Then ONE transaction (`openPaystackAttempt`, `lib/server/product-link-paystack-orders.ts`) re-reads the order (still pending, no checkout yet) and the stored Paystack key, writes `paymentAttempts/po-{orderId}` (`orderId`, `amountCents`, `currency: "ZAR"`, `mode`, `keyFingerprint`, `paymentLinkId: ""`) and sets the order's `paystackReference` and `livemode`. Only then is `initializePaystackTransaction` called, with exactly that key; the callback is the thanks page with the token. A disconnect or key switch that lands first makes the transaction retry; one that lands after finds the attempt open and flags it.
- **Failure closes both.** Paystack refusing or not answering marks the attempt `refused` and the order `failed`, so it can never be paid; so does a missing connection (503) or an order that is no longer pending.
- **Dedupe** is the same in-memory request-id dedupe, keyed also by the email: the same id with another email is another buyer and another order.
- **Reconcile** (`reconcileProductOrderCharge`, `lib/paystack/product-order-reconciler.ts`; `reconcilePaystackCharge` hands `po-…` references to it). The webhook body gives only the reference. The attempt must exist, belong to this sub-account and name this order; the verifying key must be the attempt's (else the attempt and the order are flagged); Paystack's verify answer (same tenant key) must be a success for this reference. The pending → paid transition is the SAME `settleProductLinkPayment` the Stripe path uses, with `matches` = `requested_amount` equals the order total, Paystack's `amount` is not below it, the currency equals the order's, and Paystack's `domain` equals the attempt's mode. Any other result **holds** the order (`heldAt`, never paid, no release path, same as Stripe) and flags the attempt and the order. Money for an order already failed is flagged, never dropped. A paid order settles its attempt, then runs `finishPaidProductLinkOrder` — the one contact step, the one `order.paid` claim and the one `sendOrderConfirmationAfterResponse` that the Stripe path also calls — so a replay of `charge.success` changes nothing and sends no second email, and a crash after the paid commit is repaired by the redelivery. Paystack could not answer → 503 so it redelivers.
- **Flags.** `flagPaymentAttempt` puts an attempt's reason on its order's `attention` when the attempt has an `orderId` (it has no link to carry it). A flagged order gets no confirmation email and its thanks page shows "a quick check" instead of the download, as on Stripe.
- **A flag does not outlive a matching payment.** When a verified, fully matching payment settles an order whose attempt was flagged (the usual case: the key was replaced mid-checkout and later reconnected), `recoverFlaggedOrder` runs before the confirmation: if the attempt's reason is the order's only `attention` it is cleared (`attention: null`, `attentionOpen: false`), otherwise "Reference X has since been recorded." is appended once and the other reason stays (so no email until the operator resolves it). A held order (an amount, currency or mode mismatch) is never touched: held and flagged for good, and a held order says why it is held, not the older flag.
- **Lifetime: 24 hours.** Paystack sends no expiry event. `expireStalePaystackOrders` (`lib/server/paystack-order-expiry.ts`, the `paystack-order-expiry` job of daily-housekeeping, no new schedule) takes the open buy-page attempts older than 24 h (the existing `state`/`paymentLinkId`/`createdAt` index) and asks Paystack with the attempt's own key: `success` is reconciled like a webhook (this also hears a payment whose webhook was never registered), `abandoned`/`failed`/`reversed`/unknown expires the order (`markOrderExpired`: only a pending, unheld, unflagged one) and refuses the attempt, anything else (ongoing, pending, queued…) waits for the next run until the attempt is 7 days old, then closes the same way, so a stuck one cannot hold a place for ever; no answer waits for the next run. At most 25 Paystack calls and 40 s per run, oldest first; an attempt (open, or flagged by a connection change) whose key is no longer the workspace's can't be asked, so the sweep expires its pending, unheld order and closes the attempt WITHOUT calling Paystack, keeping the order's attention note (a payment that still lands is flagged for a refund) — but only once the attempt is **72 h** old, not 24: this cannot be undone, and Paystack retries a webhook for about 72 h, so a payment that was merely delayed still finds its order pending. A flagged attempt also waits 24 h after it was flagged (`flaggedAt`, stamped when the attempt is flagged; absent on older flags, which then go by age alone) before its still-pending order is expired, so a key change near hour 71 still gives the operator a day. When the order is NOT pending and unheld (paid, held, failed, already expired or gone), only the attempt is closed and the order is left exactly as it is, so the attempt stops taking up the sweep's read window. The flagged read starts at 72 h (every row in it is then actionable: asked if its key is the workspace's again, retired if the key is gone), so a pile of flagged buys that can't be acted on yet never fills the read window and pushes other workspaces out; an OPEN attempt on a gone key (the connection change flags those, so this is a safety net) is flagged on sight, for all of that workspace's attempts at once, once per run, and the read restarts; this flagging is silent (the orders carry the flag in Reports → Payments, but no email per order) with one error-level log per workspace per run. A flagged attempt whose key is the workspace's again (disconnected, then the same key reconnected) is asked about like an open one once past 72 h, when its order is still pending and unheld: `abandoned`/`failed`/`not_found` expire the order (its flag kept) and close the attempt, `success` reconciles it (and lifts the flag), and the ask counts against the per-workspace cap. A held order and a paid order are never expired by the sweep. It uses the same index (`state`, `paymentLinkId`, `createdAt`) with `state == flagged`, so no index change. One workspace cannot starve the others: after three unresolved asks in a run (no answer, such as a revoked key answering 401, or a payment still ongoing) the rest of its attempts wait for the next run, and the read continues past the first page (up to 10 pages). The summary counts `expired` only for orders the sweep actually moved, and `errors`; a workspace whose key Paystack rejects (401/403) is listed in `keyRejected`, is not an error, and its admins get ONE email per key ("Paystack rejected your key — reconnect under Settings → Payments"; flag id carries the key fingerprint, so a replaced key rejected later is a new flag); Firestore write failures inside a run are counted apart as `writeErrors`; keys rejected in two or more workspaces are logged at error level ("Paystack rejected keys in N workspaces") and reported in `keyRejected`, never thrown (each is that tenant's own problem, and a 500 would retry daily-housekeeping for everyone); the job throws (answers 500, QStash retries all of daily-housekeeping, logged at error level) only for a Paystack outage: every ask failed with a network, timeout or 5xx error across at least two workspaces. An expired order is terminal: a payment that still lands is flagged, never dropped. The connection-change sweep (`attempt-sweep.ts`) agrees: an abandoned buy under 24 h old stays open (and is flagged by the change), an older one is closed and expired with it, so a key change flags no old abandoned clicks. A reference Paystack has never heard of (404) leaves a buy under 24 h old open with its order pending, for the expiry sweep to close both; past 24 h the sweep closes both at once.
- **Webhook not registered.** Paystack is "ready" on a connection alone, exactly as for payment links: without `webhookSeenAt` the webhook may not be registered, a payment is then not heard, and the order stays pending until the 24 h sweep verifies it with Paystack (the buyer sees "processing" until then).
- **Webhook payload.** The `order.*` subscriber payload (`OrderApiObject`, `serializeOrderForApi`) is unchanged for every existing order. A Paystack buy-page order carries `stripe_checkout_session_id: ""` and an extra optional `paystack_reference` (`po-{orderId}`); the field is absent otherwise.
- **Refunds.** Only Stripe's `charge.refunded` is wired to orders. A refund made in the Paystack dashboard is not reflected on the order (status, `refundedCents`, revenue): the operator records it by hand.
- **Not live-verified:** no charge has been taken through this path. The live walk is one R10 product buy on a live Paystack key, refunded after.

### Delivery (F4 entitlements)

A paid `product_link` order delivers what its `deliveries` snapshot promised (never the live product, and whatever the Sell online gate says now: a paid buyer is always fulfilled). `grantForOrder` (`lib/server/entitlements-service.ts`) runs from the one shared tail, `finishPaidProductLinkOrder`, after the confirmation email, in the same `runAfterResponse` job, so it is identical for Stripe and Paystack.

- **One grant per order and product.** The entitlement is `entitlements/{orderId}_{productId}` (tenancy keys on every doc). Its claim runs in a transaction that re-reads the ORDER, so a refund, hold or flag that landed after the caller read it creates nothing; an entitlement already `done` is skipped (a replay), one `sending` inside a 2-minute lease is skipped (a concurrent confirmation), a `failed` one is retried by the next confirmation, a `revoked` one never is.
- **Eligibility** (`orderDeliverable`): `paid` or `partially_refunded`, no `heldAt`, and no open `attention` flag. Pending, expired, failed and refunded orders, and any held or flagged one, get no entitlement, member, purchase or email. A flag marked resolved no longer blocks (that is how staff release a reviewed order).
- **Community.** The buyer's member is found or created by the order's email (`ensureMember`). A deactivated member, or one banned from the group, is a recorded `DeliveryError` and nothing is granted. Otherwise the group (an active membership is left as it is, so a moderator is not reset) and, for a course product, the course are granted through order-backed purchases with the fixed ids `order_{orderId}_{productId}_g|c`, amount 0, `orderId` set, `grantedByUid` `system:product-order`, then marked paid with `paidOrderId`. An order-backed pending purchase is never reused by a member's own purchase request. The buyer gets a sign-in link valid 24 hours (purchase emails are opened late), joining the group on verify. Community switched off, or no email sending, still grants but records a failure saying no mail was sent. That sign-in email is sent with `archive: false`: its link is a live bearer sign-in, so it is never written to the contact's Conversations thread (the download email is archived like any customer mail). The link is single use: the verify route keeps its use record until 5 minutes after the link expires. The member is created from the email the buyer typed, unverified; sign-in still needs a link sent to that address.
- **Download.** The link is re-checked as public https at the sink. The order confirmation already carries it, so the delivery emails it only when the confirmation did not go out (`confirmationEmail.state !== "sent"`) or could not carry it.
- **Refund racing the grant.** The order is re-read right before either email is sent. If it was refunded, held or flagged after the claim, nothing is mailed and the entitlement is marked `revoked` (it counts as skipped, not failed; access already given stays until staff remove it).
- **Failures never throw.** They are written to the entitlement (`fulfilment.state: "failed"` plus a message safe to show, never a provider error), to the order (`deliveryStatus`, the roll-up for the Payments report) and to the contact timeline (`product_delivered`, `delivery_failed`, `delivery_revoked`).
- **Staff Re-send delivery.** `POST /api/sub-accounts/[id]/orders/[orderId]/redeliver` (sub-account admins and the agency owner, like resolving an order flag; not an agent tool). It re-runs every delivery on a deliverable order with `resend`: community grants are idempotent so only the sign-in email goes again; a download link is mailed again even after the confirmation carried it. A held, flagged, refunded or pending order answers 409. Reports > Payments shows each product order's `deliveryStatus` (the failure message, or Delivered) and, for admins, a **Re-send delivery** button on any order the server would re-send (NOT browser-verified).
- **Refund.** A full Stripe refund revokes the order's entitlements (`revokeForOrder`) so a re-send cannot deliver them (if the revoke fails it is logged at error level and the order is flagged `attention`, since a replay of the refund event stops at the recorded refund and would not retry it); community access already granted stays until staff remove the member. Paystack refunds are not reconciled by us today, so a Paystack order refunded in Paystack's dashboard keeps its entitlement active (accepted, same as the order status itself).
- **Thanks page.** A paid community order (email configured, no recorded delivery failure) adds "Check your email for a sign-in link to {community name}."

## What's intentionally NOT in v1

- **Stripe Connect.** Explicitly NOT the chosen path — see the Payments v1 note above. Connect makes each buyer a Stripe *platform* (platform profile + Stripe review per buyer, KYC per client). Tier 1 (own restricted key) ships instead; Connect remains a later option behind one branch in `getSubAccountStripe()`.
- **Webhook auto-mark-paid.** PayPal.me has no payment-status callback — the operator marks PayPal invoices paid manually. Payments v1's Stripe rail fixes this for card payments (Phase B wires it into invoices).
- **Recurring/subscription products** — one-off only.
- **Partial payments / deposits.** Defer until asked.
- **PDF download in v1?** Already shipped — operator's PDF button on the detail page + recipient's "Download PDF" link on the public invoice view ([src/lib/quotes/pdf-document.tsx](../../src/lib/quotes/pdf-document.tsx)).
- **PayPal Invoicing API or Partner Referrals.** Full PayPal integration would give webhooks + branded invoices but requires per-sub-account API credentials. paypal.me is enough for MVP.

## Setup contract

**No new env vars.** PayPal.me is a public username, not a secret — no encryption layer, no `SUB_ACCOUNT_KMS_KEY`, no platform credentials. Sub-account owners paste their PayPal.me username under Settings → Payments and they're done. Reuses `RESEND_API_KEY` + `EMAIL_FROM` (invoice email send), `AUTOMATIONS_TOKEN_SECRET` (public-link HMAC), Firebase (storage), `NEXT_PUBLIC_APP_URL` (public URL construction).
