# Client Billing v1 (agency → sub-account plans + paywall)

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

GHL "SaaS mode" analog: the agency owner packages features into monthly **plans** and charges each sub-account through the **deployment's own Stripe account** (one agency per deployment → no Stripe Connect, no platform cut — the money lands in the agency's Stripe). Distinct from (a) the agency's own `users/{uid}` subscription and (b) the sub-account's client-facing payments (PayPal/quotes) — this is the agency billing ITS clients for the workspace itself.

## Model

- **Plan** (`agencies/{agencyId}/plans/{planId}`, [src/types/billing.ts](../../src/types/billing.ts)) — name + monthly price + an **optional annual price** + a bundle over the existing feature gates (`PLAN_GATE_KEYS`, all agency gates minus the parked Get Leads; `*HiddenWhenDisabled` flags stay manual). Creating a plan creates a Stripe Product + recurring monthly Price, **and — when `priceAnnualCents` is set — a second recurring Price with `interval: "year"`** on the same Product (stored as `stripeAnnualPriceId`). The agency types the annual amount directly (no auto-discount — e.g. 10× monthly = "2 months free"). Price edits mint a NEW Stripe Price (immutable) and deactivate the old one — existing subscribers keep their signup price; **monthly and annual prices edit independently** (set annual to `null` to remove it → the yearly Price deactivates). Gate edits **re-apply to every active/past_due sub-account on the plan**. Archive = no new assignments, both prices deactivate, live subscriptions untouched.
- **Billing cadence is chosen at ASSIGNMENT, not on the plan.** A plan offers both cadences; the agency picks monthly vs annual per sub-account when it assigns (`assignPlanToSubAccount({interval})`). That resolves the interval-correct Stripe Price and stamps it on `billing.stripePriceId` — so **checkout + the webhook lifecycle are interval-agnostic** (they just consume the stamped price). Display helpers live in [status.ts](../../src/lib/billing/status.ts): `formatBillingPriceWithInterval` (adds `/mo`|`/yr`), `monthlyEquivalentCents` (annual ÷ 12 for the MRR roll-up).
- **Per-sub-account state** (`SubAccountDoc.billing`, type `SubAccountBilling`) — `status: comped | pending | active | past_due | canceled`, plan denorms (`planName`/`priceCents`/`currency`), **`billingInterval: "month" | "year" | null`** (the chosen cadence; `priceCents` is the per-interval charge — the yearly amount for annual), `specialPriceCents` (per-client override → one-off Stripe Price at the SAME interval on the plan's product), Stripe customer/subscription ids, `checkoutTokenHash`, `graceUntil`. **Absent field = comped** — the default for every legacy + new sub-account, so nothing changes until a plan is assigned. Legacy docs missing `billingInterval` read as monthly. Server-only writes (subAccounts client writes are already `false` in rules).
- **Effective state** is derived at read time by [src/lib/billing/status.ts](../../src/lib/billing/status.ts)::`effectiveBillingState()` (client-safe, no cron): `past_due` + `graceUntil` in the future = "grace" (banner), past it = "lapsed" (paywall). `BILLING_GRACE_DAYS = 7`.

## Flow

1. **Plans** managed at **Agency → Client billing** ([src/app/(dashboard)/agency/billing/page.tsx](../../src/app/(dashboard)/agency/billing/page.tsx)) — plan cards + a Clients table (plan, live status badge, per-currency MRR roll-up). Routes: `GET/POST /api/agency/plans`, `PATCH/DELETE /api/agency/plans/[planId]` (owner-only, `requireAgencyOwnerAny`).
2. **Assign** from the Manage dialog's Billing section ([src/components/agency/sub-account-billing-section.tsx](../../src/components/agency/sub-account-billing-section.tsx)) → `PATCH /api/agency/sub-accounts/[id]/billing` with `{action: "assign" | "comp" | "sendLink", interval?: "month" | "year"}`. A cadence chooser appears in the Billing section only when the selected plan has an annual price; `interval` defaults to monthly. Fresh assignment → `status: "pending"` + a tokenized checkout link (HMAC + nonce, only the SHA-256 hash stored — quote-token model, [src/lib/billing/token.ts](../../src/lib/billing/token.ts); re-sending rotates the hash and kills old links). Assignment onto a LIVE subscription = plan switch: the Stripe subscription item moves to the new price (prorated) and the new gate bundle applies immediately.
3. **Checkout**: the emailed/copied link resolves at the public `/pay/[token]` route (in middleware `PUBLIC_PATHS`) → verifies token + hash → 303 into Stripe Checkout (`metadata.kind = "subAccountPlan"` on BOTH session and subscription). Logged-in sub-account admins can instead pay from the in-app activation screen via `POST /api/sub-accounts/[id]/billing/checkout`. Post-checkout landing: `/pay/[token]/status` (server-reads live status).
4. **Webhook lifecycle** ([src/lib/stripe/webhooks.ts](../../src/lib/stripe/webhooks.ts) routes by `metadata.kind` so unrelated checkout kinds never see these): `checkout.session.completed` → `active` + **apply the plan's gate bundle** (fresh plan lookup) — **once per payment**: the session id / Paystack reference is recorded in `billingActivations` atomically with the activation, so a redelivery (even after cancel or re-assign) is a no-op, and a new payment for a comped workspace, a different plan, or an already-active one is recorded as a `payment.flagged` billingEvents row instead of applied (Pre-ledger activations: Paystack's are recognised by `billing.paystackReference`, Stripe's by the stored subscription while still active. **Known gap:** a Stripe workspace activated before the ledger shipped and cancelled since has no record left, so a redelivery of its original checkout inside Stripe's ~3-day retry window can still re-activate it; the window closes 3 days after deploy); `customer.subscription.updated` → status map (`past_due`/`unpaid` → past_due + stamp `graceUntil` once per episode; `active` → clear it); `.deleted` → `canceled`. While `pending`, only a transition to active is accepted (half-finished checkouts emit incomplete/expired noise). A cancelled or pending workspace with no stored subscription ignores events that name one (a late `.updated` behind its `.deleted` cannot revive it). Paystack's `subscription.create` is matched by customer **and** plan when a customer backs several workspaces; still ambiguous → nothing stored, `subscription.flagged` row. A Paystack plan switch claims `billing.retiringSubscriptionId` in a transaction (a second concurrent switch is refused with 409; the claim expires after 10 min), opens the new subscription before disabling the old, ignores the old code's disable webhook while the claim holds, and after a failed create asks Paystack whether the new subscription exists — only a Paystack 4xx is reported as "nothing changed"; a timeout/5xx says to check the Paystack dashboard before re-assigning.
5. **Client-side states** ([src/components/billing/billing-guard.tsx](../../src/components/billing/billing-guard.tsx), mounted in the `/sa/[subAccountId]` layout inside the provider): grace → dunning banner (+ "Update card" → Billing Portal); pending → activation screen; lapsed → hard paywall ("Pay & restore access"). **The agency owner is never walled** — they see a slim notice and keep full access. Settings gains a self-gating "Your subscription" card ([sub-account-plan-billing-section.tsx](../../src/components/settings/sub-account-plan-billing-section.tsx)) with Billing Portal access (`POST /api/sub-accounts/[id]/billing/portal`).

## One-time charges (agency → client, e.g. "Web design — $500")

Independent of plans (works for comped clients too): the agency owner bills a sub-account's client ONCE through the deployment's Stripe. Top-level `billingCharges/{id}` docs (server-only writes; `pending → paid | canceled`), charge-domain-separated HMAC tokens (`issueChargeToken` in [token.ts](../../src/lib/billing/token.ts) — a plan token can never verify as a charge token) resolving at the public `/pay/charge/[token]` (303 → Stripe Checkout **`mode: "payment"`** with ad-hoc `price_data` — no Stripe Product created; reuses the sub-account's Stripe customer when one exists) + `/pay/charge/[token]/status` landing. Webhook: `checkout.session.completed` with `metadata.kind = "subAccountCharge"` → marks paid (idempotent), records `billingEvents` (`charge.created/paid/canceled`), emits the `billing.charge.paid` outbound webhook event. Surfaces: a "One-time charge" block in the Manage dialog's Billing section ([sub-account-billing-section.tsx](../../src/components/agency/sub-account-billing-section.tsx) — description + amount → create & copy/email link, charges list with copy-fresh-link + cancel) and the `create_one_time_charge` Agency Assistant capability (confirm-gated, duplicate guard: identical pending description+amount refuses and points at the existing link). Cancel voids the link (`tokenHash: null`); paid charges refuse cancel (refund via Stripe dashboard). Routes: `GET/POST /api/agency/sub-accounts/[id]/billing/charges`, `PATCH(sendLink)/DELETE .../charges/[chargeId]` (owner-only). No new env vars; no rules deploy (`billingCharges` is server-only, default-deny).

## Agency Assistant capabilities

The Agency Assistant (AI Suite, agency level) can drive the whole flow by chat — three registry entries in [src/lib/ai-suite/capabilities/](../../src/lib/ai-suite/capabilities/) (`billing-plans.ts`, `billing-charges.ts`), each wrapping the same billing-service the UI uses (owner-only, tenant-anchored, `BillingError → CapabilityUserError`):
- **`list_billing_plans`** (readonly lookup) — plans with id / price / feature count / status, so the model can resolve a plan id by name.
- **`create_billing_plan`** (confirm-gated write) — monthly price (dollars) + optional annual + `includeAllFeatures` or a `features` list (friendly gate slugs from `FEATURE_GATES`). Calls `createPlanForAgency`; result carries the new plan id for chaining. Two guardrails: the tool description makes the model (a) ask the user for an explicit plan name rather than inventing one, and (b) run `list_billing_plans` first to spot duplicates — AND `execute` enforces a server-side duplicate guard regardless (refuses an active plan with the same name, or an exact functional twin — same monthly price + same gate bundle — pointing at `assign_billing_plan` instead).
- **`assign_billing_plan`** (confirm-gated write) — assigns a plan to a sub-account (`interval` month/year, optional special price) via `assignPlanToSubAccount`; returns the checkout link when the assignment is pending.
- **`billing_overview`** (readonly lookup; chat + agent) — every sub-account's effective billing state (comped / pending / active / grace / lapsed), worst first, with MRR computed exactly as the agency billing page does (`isMrrEligible`: active + grace, `monthlyEquivalentCents`, per currency). An agency API key sees only the sub-accounts it reaches. Ported from upstream 1.0.40 (N2b).
- **`comp_client`** (confirm-gated write; chat only) — `compSubAccount`: comps the client and cancels a live subscription on the configured provider (Paystack or Stripe). Cancelling can't be undone, so no API key may call it. The card names the client by the model's label; execute refuses unless that is the stored name (same for `set_usage_limits`). `compSubAccount` fails closed for the tool and the Manage dialog alike: when the provider won't cancel a live subscription (or none is configured) it changes nothing and says so (the route answers 502); a subscription already `canceled` (Paystack keeps its code on record) is not cancelled again. `cancelSubscription(id, customerId)` returns `cancelled | already_cancelled`: already ended when the provider reports it ended (Paystack: not `active`/`attention`; Stripe: `canceled`/`incomplete_expired`), or when it doesn't know the subscription (404 / `resource_missing`) BUT has the customer on this account with nothing live — a not-found alone (wrong key, test vs live) throws `SubscriptionNotOnAccount` and comp fails closed. Comp holds its OWN lock across the provider call (`billing.compingSubscriptionId` + `compingSince`, 10-minute expiry), claimed in a transaction before cancelling: a plan switch refuses to start while it holds, and comp refuses while the switch's mark (`retiringSubscriptionId`) or another comp holds. Unlike the switch's mark it mutes no webhook — the subscription's own `subscription.disable` / `invoice.payment_failed` keep applying, so a comp that then fails loses nothing the provider said ([billing-comp.ts](../../src/lib/server/billing-comp.ts)). Comp writes comped while the stored subscription is still the one it cancelled (whatever status its webhooks wrote) or was cleared as `canceled`; a cancel call that failed is checked with `subscriptionEnded()` (a read), and an ended subscription finishes the comp. If the subscription was replaced (or the write fails) it releases the lock, records `comp.interrupted` and says the subscription WAS cancelled. A payment landing mid-comp (an already-open checkout) applies as usual, and comp's final write then refuses because `activatedAt` moved since the claim: the client stays active and tracked on the subscription that checkout opened (refusing the payment instead would leave that subscription billing a comped client untracked). The claim closes the open checkout link so no new checkout starts mid-comp (reopened if the comp doesn't happen, unless a newer one was minted). A Stripe plan switch, which has no claim, re-reads comp's lock right before calling Stripe. The switch's final write never lands on a comped client (it cancels the subscription it opened, `plan.switch_abandoned`), and no subscription event writes to a comped client (re-checked inside the write). A one-time charge with no currency named defaults to `usageCurrency()`, so invoicing overage bills in the currency the dialog showed it. The assistant's `create_one_time_charge` does the same when the currency is omitted, and refuses (rather than bills in a currency its card didn't show) when the client is billed in another currency than the provider's.
- **`resend_checkout_link`** (agent only; `outbound` approval) — `mintCheckoutLink` for a client with a plan assigned and not active. Chat refuses it and points at Manage → Billing → Send link. On an agency key it is an agency-level row whose preview shows the plan, price and stored billing status and pins them; approving re-reads them and mints nothing if they changed, and refuses before rotating the token when `NEXT_PUBLIC_APP_URL` is unset (rotating first would kill the old link with no new one).
- **`sub_account_usage`** (readonly lookup; chat + agent) and **`set_usage_limits`** (confirm-gated write; chat only) — the usage ledger against the effective quotas, overage in `usageCurrency()` ([src/lib/billing/currency.ts](../../src/lib/billing/currency.ts): the plan's currency, else the provider's, ZAR on Paystack), the same answer the Manage dialog's usage route gives; and the per-workspace `usageQuotas` override (only the given units, or `clear`), whose reply shows this month's usage against each new limit and flags one already reached.
- **`deployment_setup_status`** (readonly lookup; chat only) — the Get-started banner's own evaluation (`deploymentSetupGroups` in [src/lib/setup/deployment-status.ts](../../src/lib/setup/deployment-status.ts)): titles and statuses only, never a key name or value; the Email row counts the agency's verified SMTP senders.

Combined with the pre-existing **`create_sub_account`**, a single request like "create sub-account 'Gym Junkies', then a $99/mo plan with all features and assign it" resolves to **three sequential confirm cards** (the chat route proposes one write at a time and loops) — the owner approves each. The model resolves ids between steps with `list_sub_accounts` + `list_billing_plans`.

Gate application was extracted to [src/lib/server/feature-gates-service.ts](../../src/lib/server/feature-gates-service.ts)::`applyFeatureGates()` — the ONE place that flips `*EnabledByAgency` fields (owns the email-domain tear-down + the Meta-unconfigured guard). ## Audit + events

Append-only `billingEvents` collection (server-only, mirrors `aiSuiteActions`): plan.assigned / plan.switched / comped / activated / status.changed. Outbound webhook events: `billing.plan.assigned`, `billing.activated`, `billing.past_due`, `billing.canceled`.

## Flagged payments (Attention)

Money that arrived but settled nothing — `payment.flagged` / `subscription.flagged` rows in `billingEvents` — is listed in an **Attention** section at the top of Agency → Client billing (sub-account, reason, amount, reference, date) with **Mark resolved** (`GET/POST /api/agency/billing-attention`, owner-only; records who and when in `billingAttention/{flagId}`). Order flags (`order.attention`) get the same treatment on Reports → Payments — see [products-invoices.md](products-invoices.md).

**Email, once per flag.** Plan-billing flags email the **agency owner**; order flags email the **sub-account's active admins** (the agency owner when it has none). Sent through the deployment's shared sender when `RESEND_API_KEY` + `EMAIL_FROM` are set, otherwise through the verified SMTP of the sub-account the flag belongs to (for an ambiguous subscription, the first candidate with one) — a deployment on per-sub-account SMTP has no shared sender. No sender at all → `[billing-attention] … no email sender` is logged and nothing is claimed. The claim in `billingAttention/{flagId}` is written before sending, so a webhook redelivery that re-writes the same flag sends nothing; a failed send is logged and recorded (`notifyError`), not retried. Code: [billing-attention.ts](../../src/lib/server/billing-attention.ts), [billing-attention-notify.ts](../../src/lib/server/billing-attention-notify.ts). No rules or index deploy: all reads go through server routes.

## Usage rebilling

Port of upstream 1.0.54 G1 (the meter) and G2 (the monthly close and charge). **NOT runtime-verified:** both switches default off and no tenant has them on, and a live walk means charging a real client, so the close has only run against in-memory Firestore with every provider call spied. Until a switch is on, the only live effect is the rebilling card in the Manage dialog.

- **Two switches, both read `=== true`, both default off.** `agencies/{id}.usageRebillingEnabled` is the master switch (Agency → Client billing; `PATCH /api/agency`). `subAccounts/{id}.usageRebillingEnabled` is per client (Manage → Usage rebilling; `PATCH /api/agency/sub-accounts/[id]/feature-gates`). Both routes refuse a non-boolean (400). The client switch is refused on (400) unless the master switch on the sub-account's stored agency is on; switching off is always allowed. Both are agency-owner only, switching either on re-reads the caller's live `agencyMembers` row (`activeOwnerRefusal`), and off→on stamps `usageRebillingSince`. Each real change writes a `usage_rebilling.updated` audit event (agency-level for the master switch).
- **One transaction per flip** ([usage-rebilling.ts](../../src/lib/server/usage-rebilling.ts)): the doc is re-read and written in the same transaction (the client switch also re-reads the master switch there), so concurrent toggles write one change, one `usageRebillingSince` and one audit row. Audit rows are written after the commit, from what the transaction changed.
- **Master off cascades.** Switching the master switch off also switches every rebilled client of that agency off in the same transaction (in chunks of 400 when there are more), with one audit row per client that changed. Each chunk's client audit rows are written as soon as that chunk commits (the agency row after the first), so a chunk that fails leaves nothing committed unaudited; re-sending "off" (the master already off) clears and audits the stragglers. If the master is switched back on mid-cascade, the later chunks clear nothing, so a client the owner has just switched on stays on. Switching the master back on reactivates nobody; each client is switched on again individually.
- **What "rebilled" changes.** The rebilling card's usage-charge preview, and the monthly close below: the agency usage route returns `rebilling.previewCents` (the overage total) while both switches are on, `null` otherwise (`usageRebillingState()` in [usage-meter.ts](../../src/lib/server/usage-meter.ts), read fresh, never cached). The existing overage line in the dialog and in `sub_account_usage` still shows whenever rates are set, switches or not (its maths was corrected, below). Quotas cap sends as they did; enforcement is unchanged.
- **Currency.** `usageCurrency()`: the plan's currency, else the provider's (ZAR on Paystack, USD on Stripe). Upstream's `"usd"` default is not ported.
- **Maths (corrected in G1).** `computeOverage()` (both the overage line and the preview) works in integer minor units with BigInt: each unit's line is `overUnits × rate ÷ per` (per = 1, 1,000 tokens or 60 voice seconds), rounded half-up once; the total is the sum of the rounded lines. The old float maths could land a cent low on a half (4,100 tokens at 15c per 1k showed 61c; it is 62c), so some AI-token and voice figures move by up to a cent per line. It is display only today; nothing was charged from the old figure. A fractional stored rate is rounded half-up first. Overage exists only past a quota and only for a unit with a rate. A malformed counter (NaN, infinite, negative, non-number) bills nothing, a fractional one bills whole units, and a line that would take the total past `Number.MAX_SAFE_INTEGER` is skipped rather than rounded. `sanitizeUsageRates` caps a stored rate at 1,000,000 minor units (`MAX_USAGE_RATE_CENTS`) and drops one that rounds to 0. Fixtures: [usage-meter.overage.test.ts](../../src/lib/server/usage-meter.overage.test.ts).
- **Not ported yet (upstream 1.0.54):** the AI-reply, web-voice, shared-SMS, softphone and website-read counters; per-call AI cost; flat feature fees; the spend ceiling (which on upstream lifts the quota cap for priced units of a rebilled client); upstream's overage semantics (no allowance = billed from the first unit); the pricing editor. These are unit G1b. The monthly close, carry-over and usage charge are G2 (below); the overdue banner is G3.
- **Never ported: upstream's UTC month key.** `usageMonthKey()` stays on server-local time, because our clients are SAST and a usage month must end at local midnight (decided 2026-10-29). velo-server runs Africa/Johannesburg, and the service sets no `TZ`. A buyer copy on Vercel runs in UTC, so its months are UTC.

### Monthly close and charge (G2)

- **When.** The `usage-close` job in [daily-housekeeping](../../src/app/api/cron/daily-housekeeping/route.ts) runs every day (05:00 SAST). The first run of a new month closes the previous one (server-local month, like the ledger); every later run finds it closed and only sends reminders. A missed day is recovered the next day.
- **Freeze** ([usage-billing-service.ts](../../src/lib/server/usage-billing-service.ts) `freezeMonthForSubAccount`): one transaction re-reads the client, its agency and the month, and writes `subAccounts/{id}/usage/{month}.closed` once. A month is billed only if it STARTED with both switches on: both `=== true` in those reads, and each `usageRebillingSince` readable and at or before the month's first instant. A client enabled mid-month is billed from its first full month; a missing or unreadable `since` with the switch on fails closed. Otherwise the month is closed `skipped` (with `skippedReason`) and nothing is queued. The total is `computeOverage` plus an amount carried in from the last billed month: only from one of the two months before it, and only in the same currency, otherwise it is not applied, a warning names it, and it stays on that month's ledger as `carryOutCents`. Under `USAGE_MIN_CHARGE_CENTS` (500, R5/$5) nothing is charged: the amount is carried into the next month. Each freeze and skip writes a `usage.frozen` / `usage.skipped` row in `billingEvents`.
- **Mint.** The charge is a `billingCharges/usage_{subAccountId}_{month}` doc (`kind:"usage"`, `usageMonth`, `lineItems`, `dueAt` = 14 days from creation, `remindedAt`, `emailedTo`) written with `create()`: a re-run, a second concurrent run or a re-queued month hits ALREADY_EXISTS and creates nothing. It passes the same amount/currency checks as a manual charge, ceiling included; an out-of-range charge is refused, nothing is written, and the month stays queued and is reported in `refusals` every run. A missing or short `AUTOMATIONS_TOKEN_SECRET` (under 16 characters) is checked first, before anything is written, and is a refusal ("token secret not configured"), for invoices and reminders alike. **Over the ceiling** (100,000,000 minor units, R1,000,000 / $1,000,000): after the entry has sat queued for 7 days the month is withheld (`withheldReason: "over ceiling"`, a `usage.withheld` row, reported once) instead of repeating forever. To bill it by hand, create manual charges from the agency charge list, each under the ceiling and summing to the amount in the ledger's `closed.totalCents`; do that within the 7 days or afterwards, since a withheld month is never re-queued. A ceiling bill that was truly meant should be raised in code (`MAX_PRICE_CENTS`), not worked around. It is born with NO live pay link (`tokenHash: null`) and no stored URL: the raw token exists only in the email it is sent in: it is *staged* (`stageChargeLink`) before the send and made live (`commitChargeLink`, a transaction that refuses a paid or cancelled charge) only after the send succeeds, so a failed reminder never kills the link already out there and a reminder that does go out retires the one before. Everything a send needs (recipient, sender) is checked before a link is staged. The agency's own re-send (`mintChargeCheckoutLink`) uses the same transaction. The full eligibility rule (both switches AND each `since` at or before the month's start, the same helper as the freeze) is applied again just before the charge is minted, so a client toggled off and on between freeze and a delayed mint is not billed. If either is off and **no charge exists**, nothing is minted. If the charge exists but its invoice was **never emailed**, it is cancelled (`status:"canceled"`, token cleared; unless an email is being sent at that moment), so no reminder can follow. Either way the ledger gets `closed.withheldAt` and `withheldReason`, `usage.withheld` (and `charge.canceled`) rows are written, and the month is not billed later. Whatever was carried INTO a withheld month is not lost: it is put back on that month's ledger as `carryOutCents`, so the next billed month picks it up (within the 2-month rule). Only the withheld month's own usage is dropped. Once the invoice **has** been emailed the debt stands: reminders continue even after a switch goes off. A failed invoice email followed by a switch going off is the "never emailed" case (cancelled). Currency is `usageCurrency()` (the plan's, else ZAR on Paystack).
- **Paying.** The emailed link is the existing `/pay/charge/[token]` → `createChargeCheckoutSession` → `provider.createOneTimeCheckout`, so it runs on whichever rail the deployment uses. Paystack opens a payment page only for an email: `createUsageCharge` refuses a Paystack usage charge with no recipient (`BillingError` 422) before writing anything, the month stays queued and the refusal is logged on every run until the contact is set. The recipient is `billingRecipient()`: the workspace's account contact, else the earliest-added active admin member who is not an agency user (not the agency owner, no `agencyMembers` row; ties break on uid). If a candidate's join time can't be read the choice is undeterminable and it returns nothing (refused on Paystack). At checkout the fallback applies to usage charges on Paystack only; a manual charge, and anything on Stripe, still uses the account contact alone.
- **Settlement needs no new code.** The agency Paystack webhook (`charge.success` → `settleClientBillingPayment`) and Stripe's checkout webhook already settle any `billingCharges` doc by `chargeId` (Paystack: exact amount, currency and sub-account must match, else the money is flagged under Attention). `client-billing-payment.usage-charge.test.ts` proves it for a usage charge.
- **Email and reminders.** The invoice goes through the platform sender (shared sender, else the workspace's verified SMTP) once, claimed on the charge so overlapping runs send one; a failed send clears the attempt marker, releases the claim and tries again tomorrow for 7 days; a stamp (`emailAttemptedAt`) is written just before each send, so a run that died mid-send is read as "may have gone out" (the debt stands, never cancelled on a switch-off). With nobody to email, or no sender, or a failed send, the charge/entry stays and the case is reported in `refusals` every day. If no invoice has gone out 7 days after the charge was created (and none was attempted), the charge is **cancelled**, the ledger gets `closed.withheldAt` with `withheldReason: "invoice could not be sent"`, `charge.canceled` and `usage.withheld` rows are written, and it is reported once: an un-emailed debt does not stand. If the `emailedTo` write fails after a send, the entry stays queued and the invoice is sent again once the claim times out (at-least-once, by design). Reminders go 3 days before, on, and after the due date (one stamp each in `remindedAt`, by local calendar day), only for a `pending` charge whose invoice was emailed; the recipient is resolved before the stamp is taken (it is the CURRENT `billingRecipient()`, not the `emailedTo` address the invoice went to), and a failed send gives the stage back (reported as a refusal). A non-string contact or member email is treated as absent. The job's result carries `failed` and `refusals`. A **permanent refusal** (a `BillingError`: Paystack with no email, an amount over the ceiling, the provider or app URL not configured) is held, retried each day and logged at error level, and is listed in `refusals` (sub-account, month, reason) in the response body; it does NOT make the job answer 500, because QStash would re-run the whole housekeeping job on its retry schedule every day while the cause stands. Only an unexpected or transient error (Firestore, an unhandled throw) counts as `failed` and answers 500 naming `usage-close` (`usage_close_failed`), like `api-cleanup`; those are retried the next day too. There is no billing-attention flag for it: that mechanism is for payments that arrived, not for work held back.
- **Told to a person (Attention, no email).** Every withhold, every 7-day expiry, and every refusal on the FIRST day it appears for a given (sub-account, month, reason) writes one `billingEvents` row `usage.flagged` (id `usage-flag-{sa}-{month}-{hash of reason}-{ISO week}`, written with `create()`: the same problem flags once per ISO week however many daily runs repeat it, one that recurs after being resolved flags again the following week, and a different reason flags at once; a withhold's flag has no week in its id, so it is raised exactly once). Agency → Client billing → Attention lists it with **Mark resolved**, like a flagged payment; resolving it does not stop the underlying job from re-reporting it in `refusals`. It sends no email: the existing flag email is worded for payments that arrived. A send attempted but never confirmed after 7 days is flagged as "send state unknown, check the charge" and dropped from the queue; the charge is left as it is. A reminder with nobody to send to is a refusal, not a silent skip.
- **Withhold windows.** After the entry has sat queued for 7 days: over the ceiling is withheld as `over ceiling`; Paystack with no billing email is withheld as `no billing email`, so an old month is never billed months later when a contact is finally set. Any other refusal while creating the charge (token secret, provider or app URL not configured) is withheld as `charge could not be created`. So no month is held for more than about a week, which is also what keeps a carry restored by a late withhold from missing the next month's close. A charge paid or cancelled while its invoice or reminder was going out is done and quiet: the email went, nothing is reported. The announce after a withhold (`usage.withheld` and `charge.canceled` audit rows under deterministic ids written with `create()`, plus the flag) is idempotent and throws on a write failure; a retry that finds `closed.withheldAt` already on the ledger re-announces and clears the queue entry, so a crash between the commit and the announce loses nothing and duplicates nothing. A charge cancel and the withheld ledger fields (including the carry written back) are ONE transaction, so a crash cannot lose the carry. Every withhold reason goes through the same transactional charge check (`withholdUnsent`): no charge → stamp the ledger and write the carry back, in the same transaction that read the charge doc, while the mint writes the charge in a transaction that reads the ledger (a withheld month is not minted), so a mint racing a withhold either sees the stamp or is seen by it, whichever process runs them; a pending charge never emailed and never attempted → cancel it and stamp the ledger in one commit; a charge that was emailed, or had a send attempted, STANDS and nothing is written (the carry folded into a live charge is never also written back, which would bill it twice); an email being sent right now is left alone. A charge that already exists is never re-created, so creation refusals cannot apply to it.
- **Not in G2.** Upstream's feature fees and other new counters (G1b).

### Overdue banner, paywall and Invoices (G3)

**NOT runtime-verified, and the UI is NOT browser-verified.** It stays dark: nothing is flagged unless both rebilling switches are on and a usage invoice was emailed and is overdue, and nothing is walled unless the agency has also turned the paywall on.

- **The flag.** `subAccounts/{id}.usageOverdue` (`chargeId`, `since` = the due date, `amountCents`, `currency`, `usageMonth`, `paywall`) is written only by `refreshUsageOverdue` ([usage-overdue.ts](../../src/lib/server/usage-overdue.ts)). `subAccounts` is `allow write: if false`, so no client can set or clear it (a `usage-overdue.firestore-rules.test.ts` case per role proves it; it runs under `pnpm test:rules`, which skips locally without `FIREBASE_ADMIN_*`). No rules change was needed. Members can read it: it drives the guard.
- **When it exists.** In one transaction: the client's AND the agency's `usageRebillingEnabled` are `=== true`, and the oldest `kind:"usage"` charge that is `pending`, has `emailedTo` set and whose due day (server-local) is before today. Anything else clears it, so turning a switch off lifts the banner and wall at once (`setClientUsageRebilling`, `setAgencyUsageRebilling` re-check).
- **When it is re-checked.** A usage charge being paid (including a webhook redelivery, which clears a flag a failed refresh left behind), a usage charge being waived (`cancelOneTimeCharge`), either rebilling switch changing, the paywall setting changing, and every daily close (`sweepUsageOverdue`: every client with a pending usage charge plus every flagged client). A charge goes overdue the day after its due date, picked up by that morning's close. The sweep's scan (and the agency re-check) is tried three times, waiting 250ms then 750ms between attempts; if it still fails the daily close counts it as a failure (the housekeeping job answers 500 and QStash retries). Waiving an already-waived charge re-checks too, and a charge of 0 or less is never flagged (the close cannot mint one: it charges only from 500 minor units up, and `createUsageCharge` refuses under 100).
- **Fails open, deliberately.** This is the one exception to fail-closed in this area, because the safe direction for the client is not being walled. If the refresh cannot read what it needs it clears the flag instead of keeping or setting one (and logs). The client guard reads the same way: a flag with an unreadable due date, or `paywall` that is not exactly `true`, is a banner or nothing, never a wall. The cost is a banner that can disappear until the next sweep.
- **The paywall setting.** `agencies/{id}.usagePaywallEnabled` (default off, read `=== true`; Agency → Client billing, shown only while rebilling is on; `PATCH /api/agency`, owner only, live owner row re-checked on enable, audited as `usage_paywall.updated`). It is copied into the flag as `paywall`, with `agencies/{id}.usagePaywallEnabledAt` (stamped on each off-to-on) as `paywallSince`, so the client guard needs no agency read. Off: a client sees the amber banner for as long as the invoice is overdue, with no promise to pause. On: the banner counts down to the later of 7 days (`BILLING_GRACE_DAYS`) after the due date and 7 days after the paywall was turned on, then the workspace is replaced by "Usage invoice unpaid" until it is paid or waived, so turning it on never walls a long-overdue client at once (a flag with no readable `paywallSince` is a banner only). Any agency user of the workspace's agency (owner or staff) is never walled and gets a slim notice. If the re-check of already-flagged clients fails after a flip (retried twice), `PATCH /api/agency` answers 502 with `saved:true` and the toast says so; the daily sweep is the backstop. **A paywall that was already on before `usagePaywallEnabledAt` existed shows a banner only** (a flag with no `paywallSince` never walls) until the owner turns it off and on again, which stamps the date. Likewise, re-enabling a client (its `usageRebillingSince`, stamped on each off-to-on, copied into the flag as `rebillingSince`) starts a fresh 7 days: the wall is at the latest of the due date, the paywall turn-on and the client's re-enable, plus 7 days. A comped client can be walled for usage; an unpaid subscription still shows first.
- **Pay.** The banner's and paywall's button (admins only) posts to `POST /api/sub-accounts/[id]/billing/usage-charges/[chargeId]/checkout`, which calls the same `createChargeCheckoutSession` the `/pay/charge/[token]` page calls (so Stripe or Paystack, payer email from `billingRecipient`). It stores, mints and rotates no link, so the link in the invoice email keeps working. It 404s a charge of another workspace, a manual charge or a non-doc id, and 409s a paid or waived one.
- **Invoices.** Agency → Client billing → Invoices (`GET /api/agency/billing/charges`, owner only): the agency's charges, read in pages by document id (no composite index) up to 5,000; past that the response carries `truncated:true` and the panel warns that totals may be incomplete (the id order is not creation order, so the dropped ones are not necessarily the oldest), with Outstanding / Past due / Collected-this-month totals per currency ("Past due" is the browser-side approximation of the server's overdue flag), filters, re-send (rotates the link; a usage charge warns first) and cancel/waive. The clients table shows a "Usage overdue" pill. Manage dialog: a "Billing & usage" tab holds the billing and usage sections, with a dot when something needs attention.
- **Not ported.** The "AI" Manage tab (the gate toggles stay on one Features tab), the plan editor's spend ceiling and feature fees (G1b), and the Agency Assistant's billing-overview mention of overdue usage (T4).

## Enforcement scope (v1 limitation)

The paywall is a UI-level block (the GHL behavior — data preserved, workspace inaccessible). API routes are NOT individually billing-gated in v1: a lapsed client's API keys keep working until the agency flips the API gate off. Usage metering / prepaid-wallet rebilling (email/SMS/AI markup) is the locked v2 direction — see the plan memory.
