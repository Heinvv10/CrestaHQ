# Booking pages v1

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

Native Calendly-style slot picker per sub-account. The operator configures a Booking Page (durations, working hours, optional price, optional reminder offsets) and shares the public URL `/b/[subAccountId]/[slug]`. A visitor picks a slot, the server transactionally re-verifies availability, reconciles a Contact, mints an Event, and sends an ICS-attached confirmation email. Reschedule + cancel + reminders + payment-expiry are all queued through QStash so they keep firing across Vercel cold starts.

## Data model

- `subAccounts/{id}/bookingPages/{pageId}` — page config (slug, timezone, duration, padding, working hours, required fields, optional `priceCents`, optional `reminderOffsetMinutes[]`, `status: "draft" | "published"`).
- `subAccountDoc.bookingLink` — the sub-account's **default booking link**: the URL the `{{bookingLink}}` merge tag resolves (workflows, broadcasts, WhatsApp templates, review requests) AND the link the AI agents share when someone wants to book (`buildSystemPrompt`'s channel-aware booking block — text channels share the URL, voice promises it by text). Set by admins via the **Default booking link** card on the Booking page ([src/components/booking/default-booking-link-card.tsx](../../src/components/booking/default-booking-link-card.tsx)) — pick a published booking page or paste a custom URL (Calendly etc.); saves through the existing sub-account PATCH. (The original setter died with the legacy Automations → Settings page — until this card, the tag silently resolved to "".)
- `events/{eventId}` — the existing Calendar events collection picks up two new optional fields: `bookingPageId` (denormalised back-reference) + `bookingMeta` (the recipient-typed payload + ICS uid).
- Token: bookings mint a public `bookingEventToken` HMAC-signed via `AUTOMATIONS_TOKEN_SECRET`, used in confirmation-email links so the recipient can reschedule or cancel without a login. The raw token never persists — only the SHA-256 hash on the event doc.

## Calendar types (SP3)

A page's `calendarType` (absent on legacy pages ⇒ `pageCalendarType()` derives `round_robin` when it has hosts, else `personal`):

| Type | Slots | Booking |
|---|---|---|
| `personal` | One host: that host's events + unassigned events block. No host: every event in the sub-account blocks (legacy single schedule) | Stamps the host |
| `round_robin` | Union of each host's free time | One host: `distribution` `equal` (least loaded, then `priority`) or `availability` (priority, then load); page order last |
| `collective` | Intersection — every host free (each host's own hours) | Every host: `hostUids[]`, `assignedToUid` = first. Blocks each listed host everywhere |
| `class` | Same-page bookings at the slot start are seats (`seatsPerSlot` ≥2); the day cap counts booked sessions (start instants) | One event per attendee. A hostless class page's seats carry no host, so each one is shared busy — it blocks every host's other pages for that time |
| `service` | Sized to the picked service (`services[]`, 1–20) | As round robin; stamps `serviceId`/`serviceName` |

Every caller that offers or re-verifies a slot — availability API, book route and reschedule route (inside their transactions), voice agent — goes through `resolvePageAvailability` ([src/lib/booking/resolve-availability.ts](../../src/lib/booking/resolve-availability.ts)); the rules are pure in [page-slots.ts](../../src/lib/booking/page-slots.ts). Reschedule re-verifies the event as it was booked (`MovingEvent`): all of its own host(s) — one no longer on the page keeps the page hours while still an active member, and is refused with a 409 ("… is no longer available — please contact the business to rebook") once they are not — its service, or its own length when that service is gone. A hostless booking on a page that has since gained hosts keeps the legacy shared schedule (every event blocks). The reschedule view's `excludeEventId` is honoured only for an event booked on that page. Voice refuses service pages (no service step on a call).

**Rollout:** the host readers (per-host `.ics` feed, round-robin load, reassign conflict check) query `events(subAccountId, hostUids CONTAINS, startAt)` through `queryHostEvents`. Deploy `firestore.indexes.json` and let that index finish building BEFORE shipping this code; until it does, the collective half of each read fails (logged) and only owned bookings are seen.

## Availability rules (SP3)

All optional; absent ⇒ the old behaviour. Applied in [page-slots.ts](../../src/lib/booking/page-slots.ts) / [availability.ts](../../src/lib/booking/availability.ts), so every caller of the resolver gets them.

- **Date-specific hours** — `dateOverrides[]` (`{date: "YYYY-MM-DD", ranges}`, page timezone) on the page and per host. Empty `ranges` = closed that date; an entry can also open a date the weekly hours leave closed. Precedence for one host on one date: a page entry that **closes** the date closes it for everyone; otherwise the host's own entry wins; otherwise a page entry that changes hours applies — but only to hosts on the page hours (a host with custom weekly hours keeps them); otherwise weekly hours. Max 366 per list; past dates are kept.
- **Buffers** — `bufferBeforeMinutes` (new) and `bufferMinutes` (now the *after* buffer). A new slot `[S, E)` must have `[S − before, E + after)` clear of every busy interval (manual events, other pages' bookings, external busy). This page's own bookings also keep their buffers, so two bookings on the same page are at least `max(before, after)` apart.
- **Slot interval** — `slotIntervalMinutes` (5–240, step 5): minutes between slot starts, across services too. Null ⇒ `durationMinutes + bufferMinutes`, the old step.
- **Max per day** — `maxPerDay` caps the BOOKINGS the page holds on a local date (per host on pages with hosts; booked sessions on class pages) — [day-cap.ts](../../src/lib/booking/day-cap.ts). Every status but cancelled counts: a completed or no-show booking still used the day. A date at the cap offers nothing more, and the book/reschedule re-verify refuses it. It used to cap the free slots *offered* (first N shown), which limited nothing.
- **Long busy events** — the main busy read ranges on `startAt` and looks back 26 h. Events longer than 8 h (a multi-day "Out of office") carry `isLong: true`, written by every path that sets an event's times ([long-event.ts](../../src/lib/booking/long-event.ts); booking and voice bookings are slot-sized and leave it absent), and a second query on `(subAccountId, isLong, startAt)` finds those that began up to 366 days earlier. That query runs outside the book/reschedule transaction (bookings are never long, so it needs no conflict detection) and **fails soft** — no long events, logged once — while its index is missing.
  **Rollout (owner-gated):** deploy `firestore.indexes.json` and wait for the index, deploy the app, then run `node --env-file=.env.local --experimental-strip-types scripts/backfill-event-is-long.ts --project <id>` (dry run) and again with `--apply`. Until then long events that began more than 26 h before a slot are not seen — no worse than before, when the read looked back 8 h.

**Behaviour change for existing pages:** before SP3 `bufferMinutes` was only the slot step and never padded existing events — a 15-min buffer still allowed a slot starting right when a manual event ended. It now pads busy time as the after-buffer. Slots next to the page's own on-grid bookings are unchanged (the step already leaves that gap); a slot whose after-buffer runs into an off-grid manual event, or a same-page booking closer than the buffer, is no longer offered.

## Style presets (shared with checkout pages)

Five presets — Clean, Midnight, Noir Lime, Sunset, Ocean — restyle the public booking page (`/b`, and the embed) and the public checkout page (`/co`). One table, [src/lib/checkout/themes.ts](../../src/lib/checkout/themes.ts), holds every value; the ids in `CHECKOUT_THEME_IDS` ([src/types/checkout-pages.ts](../../src/types/checkout-pages.ts)) are stored on the page doc as `themePreset` and are append-only. Both editors use the same picker ([src/components/checkout/theme-preset-picker.tsx](../../src/components/checkout/theme-preset-picker.tsx)). *Ported from upstream 1.0.40; not yet walked in a browser as of 2026-10-11.*

- **A preset is style only.** Content and layout are the same with or without one. Nothing a tenant types reaches a `style` or `class` attribute through a preset: the stored value is only ever compared against the id list, and the styles come from the table. A page's own colour (`accentColor` on a booking page, `appearance.accent` on a checkout page) is used only when `isHexColor()` passes it; anything else is ignored on read.
- **Booking — no preset = the look the page always had.** `themePreset` null, absent, or an id this build does not know all mean "no preset": the app's own tokens plus the page's optional `accentColor`, with no added markup. A preset is applied by setting the shadcn CSS variables inline on `<main>`, plus the class `dark` or `light` so the tokens a preset does not override (e.g. `--destructive`) take that scheme's values rather than the visitor's. Status text (deposit chip, errors, payment notice, confirmation) is picked from the preset's lightness through `STATUS_TEXT` and carries no `dark:` variant under a preset: `dark:` keys off `<html class="dark">`, so on a light preset it would still fire for a dark-mode visitor. Do not add a bare `dark:` utility inside this view. A page's own `accentColor` still wins over the preset's accent. "Brand default" in the picker clears the preset. `/e/[token]` (reschedule/cancel) is not themed.
- **Checkout — always a preset (upstream's files, verbatim).** A new page starts on Clean. A page with no stored preset, or an unknown one, resolves to Clean or Midnight (from `appearance.theme`) with its own accent carried over, and the editor saves that preset the next time the page is saved. Once a preset is stored the page's own `appearance.accent` no longer applies. This port also brought upstream's restyle of the page itself (the price line above the order bumps, a bolder pay button, tinted checkboxes); production had no checkout pages when it landed.
- **Only an allow-list is sent to the browser.** `/b`, the embed and `/e` hand data to a client component, and Next writes every prop into the HTML response for hydration whether or not it is rendered. So their loaders never pass a stored doc: `publicBookingPage()` and `publicBookingBranding()` ([src/lib/booking/public-page.ts](../../src/lib/booking/public-page.ts)) pick, by name, the fields the views read, and their return types are the views' prop types. To show something new on the public page, add it there and to the type. Never sent: tenancy and territory ids, `createdByUid`, hosts, working hours and rules, reminders, migration and agent-edit fields, and `meetingUrl`, `confirmationMessage` and `redirectUrl` — the meeting link reaches the booker in the confirmation email, invite and reminders, and the other two come back from the book route once a booking exists. The style fields are checked on the way (`publicBookingStyle()`, [src/lib/booking/public-style.ts](../../src/lib/booking/public-style.ts)) and a logo must be an http(s) URL; the views' own checks are a second layer. A markup-only test cannot see any of this: assert on what the server page hands on (`stringsSentToClient`, [src/test/sent-to-client.ts](../../src/test/sent-to-client.ts)) or on the raw response in Playwright. `/co` passes its form a resolved theme, never the stored page.
- **The same rule on the other public pages.** A stored colour reaches a style only through `isHexColor`: the checkout thank-you page takes `resolveCheckoutTheme()` like the checkout page (so it also follows the preset); funnels go through `funnelAccent()` ([src/lib/funnels/accent.ts](../../src/lib/funnels/accent.ts)) at the page and again in `FunnelSections`; web chat is checked at both server exits (the `/embed/chat` page and `/api/web-chat/config`, which `widget.js` writes into a style on the embedding site); public forms in `resolveAppearance()`, and the form handed to the client carries only that checked appearance; community pages through `communityBrand()`. A funnel's background image (hero and image bands), which is written into CSS `url(…)`, must pass `funnelCssImageUrl()` ([src/lib/funnels/image-url.ts](../../src/lib/funnels/image-url.ts): https, a public host, at most 500 characters, nothing that can end the `url(…)` token) in the page's loader and again in `FunnelSections`, or the image is dropped. Not yet done: a check inside `chat-window.tsx` and `widget.js` themselves, and write-side validation of a community `brandColor`.
- **Writes:** an unknown id is refused with "Unknown style preset." by `validateThemePreset` (booking routes and the agent's `create_booking_page` / `update_booking_page`) and by `sanitizeCheckoutPagePayload` (checkout routes).

- **Contrast:** every preset's button text, body text and status colours are held at WCAG AA (4.5:1) by tests that do the maths. Sunset's and Ocean's `buttonBg` are darkened from upstream's for that reason, and the checkout form picks its red and amber from the preset's lightness; both are marked `HARDENING` in otherwise-upstream files.
- **Known, and not verifiable without a browser:**
  - a dark preset combined with a dark own `accentColor`: the submit button and selected slot take the accent with white text, which can be hard to see against the dark card;
  - the embed: the preset's page background is painted on `<main>`, so a seam of the iframe document's own background may show around it;
  - native controls (the timezone list's popup, scrollbars, date pickers) follow the visitor's `color-scheme`, not the preset's — nothing sets `color-scheme` under a preset;
  - upstream tokens still under 4.5:1 and left as they are: the accent used as text (the "+ price" on a checkout bump) is 3.5:1 on Sunset and 4.1:1 on Ocean, and the checkout footnote (`faint`) is 4.4:1 on Midnight, 3.8:1 on Noir Lime and 2.5:1 on Sunset.

## Location (port 1.0.54 B2)

Each page says where the meeting happens: `location: { type, value }` ([src/types/booking.ts](../../src/types/booking.ts), helpers in [src/lib/booking/location.ts](../../src/lib/booking/location.ts)). Types: `video_link` (the page's `meetingUrl`, required for this type), `google_meet` (a unique Meet room per booking; `meetingUrl` is then an optional fallback), `in_person` (the business's address, `value`), `we_call` (the booker's phone, which the form already requires), `they_call` (the number to call, `value`) and `their_address` (the booker types an address when booking). `googleMeet` is derived from the type by the validator, never taken from the body; non-video types drop a stray `meetingUrl`. A page saved before the field existed reads through `effectiveBookingLocation()` (a `meetingUrl` reads as `video_link`). **A location is optional, including to publish** — upstream 1.0.54 requires one to publish; not ported, because every live page and the agent's booking-page tools would start failing on their next save (Hein's call).

- **Plain text only.** An address (business's or booker's) is at most 300 characters, a number at most 40 with at least 6 digits, and neither may carry `<`, `>`, a control character (C0, DEL, C1 including NEL) or a Unicode line / paragraph separator (`isPlainLocationText`); the booker's phone is held to the same rule — checked in the editor's save (`validateBookingLocation`), the book route, and again when `/b` serialises the page (`publicBookingPage` sends only `{ type, value }`, never the meeting link).
- **The event's `location`** is the "Where:" line (`eventLocationText`): `Phone call: we'll call <booker's phone>`, `At your address: <address>`, the business's address, and so on. It goes into the confirmation (text and HTML), the invite's `LOCATION` (the meeting link wins when there is one), reminders, the mark-paid confirmation and both reschedule mails, and the host's notification. Voice bookings get the same line from the caller's number. **Personal data, by design:** for `we_call` and `their_address` that line carries the booker's own phone number or home address, and it is the event's `location` — so it is written into every host's Google Calendar copy (the push's `location`), the sub-account's `.ics` subscription feed (`LOCATION`, readable by anyone holding the feed URL), the invite and the reminders. A sub-account that shares its feed URL shares those addresses and numbers with it.
- **Booker's name, email and phone** are one-line plain text at the book route (400 otherwise; a non-string field is a 400 too): the name and phone by `isPlainLocationText`, the email additionally refuses C0/C1 controls and line separators that `\s` misses. Voice bookings strip the caller's name and number to one line (`oneLineText`). In the invite, `mailto:` values have whitespace, controls and separators removed, `CN=` is a quoted-string, and lines fold at 75 UTF-8 octets without splitting a character.
- **Google Meet** needs Calendar sync on for the sub-account (`googleCalendarEnabledByAgency`), at least one host on the page, and **every** host's Google Calendar connected (status `connected`). `prepareBookingPage` refuses (400, naming the unconnected hosts) only when Meet is being **switched on**: a create, a page becoming Meet, or a Meet page going live. Any other save of a Meet page whose setup broke later (a host disconnected) goes through with a `warning` (the editor shows it; the agent's preview has a Warning row), so the page can still be edited or unpublished. The routes and the agent's booking-page tools both go through it; a duplicate whose Meet is no longer possible is copied without it, with a warning. A page saved before `location` existed is read through `effectiveBookingLocation()` by the editor, the agent's edit and the duplicate, so a legacy `googleMeet: true` keeps Meet. The editor disables the option when the gate is off or the page has no hosts (it cannot see other members' connections; the server check covers that).
- **The Meet room** is made by the booking push on the assigned host's Google copy (a collective meeting's first host) — see [Google Calendar sync](google-calendar-sync.md#google-meet). For a free booking the book route **awaits** that push before the confirmation, so the email and invite carry the booking's own link; mark-paid does the same before its confirmation (a paid hold's own push runs after the response). Both wait at most `MEET_PUSH_DEADLINE_MS` (6 s) overall (`pushBookingAndGetMeetUrlWithin`); past it the push carries on detached and its room lands on the event for reminders. A reschedule mails the link as it stands after its push. When no link is available in time (host disconnected, Google failed or slow, Meet off for that Google account) the booking still succeeds: the page's fallback link goes out if it has one; otherwise the booker's mail says "the joining link will follow", and someone in the workspace is told — the host's notification on the book route, or, when no host could be emailed (and always on mark-paid, which emails no host), a `meet_link_missing` row on the contact's timeline. A push still running at the deadline always gets that row, host emailed or not, so it can be corrected when the push ends without a room (the host's "being created" email can't be). The wording depends on why (`meetLinkMissingNote`): a push still running at the deadline says the link is being created and will appear on the booking; a push that finished without a room says to check Calendar sync and send a link.
- **NOT runtime-verified** against real Google: the Meet request shape follows Google's documented `conferenceData.createRequest` + `conferenceDataVersion=1` and is covered against a stubbed fetch and the fake provider only. Live walk pending on #1000 with a connected member.

## Text confirmation and reminders (port 1.0.54 B3)

`smsRemindersEnabled` on the page (editor: "Text confirmation and reminders"; **off by default**, absent reads as off). When on, the booker gets a text when the booking is confirmed and one at each reminder offset, sharing `reminderOffsetsMinutes` with the email reminders. It is independent of `remindersEnabled`: a page can text only, email only, or both. Bodies and the send live in [src/lib/booking/sms.ts](../../src/lib/booking/sms.ts); the reminder step's claim, hold and drop in [src/lib/booking/sms-reminder.ts](../../src/lib/booking/sms-reminder.ts).

- **What a text may say.** The public booking page lets anyone make us text a number of their choice, so a text is fixed wording plus values the operator or the system set: the business name, the page (or service) name, the time, the Meet/video link (https only, no credentials in it, capped, printed in its parsed form so a control character cannot start a new line) and the manage link. **No booker free text** reaches it: no location or address, no phone, no event title (it carries the booker's name), and the booker's name only as one plain first name (a single token of letters with at most one hyphen, each part 1 to 15 letters with at most one apostrophe, otherwise omitted; `smsFirstName`, so a hyphenated slogan cannot pass as a name). This holds for the confirmation and every reminder.
- **Who it goes to.** The contact's number must parse to a valid MOBILE number whose REGION is the sub-account's home country (`defaultPhoneCountry`), sent as E.164. The region, not just the calling code: +1 also covers Jamaica and the other Caribbean countries, which are refused for a US/CA workspace (US and CA text each other, and a US workspace also texts PR, GU, VI, AS and MP). **Turning a page's texts on is refused until the workspace has chosen a phone country** (Settings → Phone region; an unset one reads as US, so a workspace elsewhere would switch texts on and reach nobody): the page save returns a 400 and the editor shows a warning. Duplicating a page with texts on in such a workspace copies it with texts OFF and a warning (like a payment gate the workspace lost), rather than failing the duplicate. Premium-rate, toll-free, shared-cost, landline-only and short numbers, letters (vanity numbers) and extensions are refused. A refused number gets no text and a note on the contact's timeline. The calling code is compared, so +1 covers the US and Canada.
- **Daily caps** (`lib/booking/sms-caps.ts`; UTC day): at most **6 texts per destination number** per sub-account (one booking is a confirmation plus two reminders, so two bookings fit) and at most **200 per sub-account**. Counters live in `subAccounts/{id}/bookingSmsCaps` and are read, checked and incremented in the **same Firestore transaction** that creates the text's claim doc, so concurrent deliveries cannot both take the last slot. Over a cap, or a transaction that cannot commit, means no text and a logged reason (`cap_number`, `cap_subaccount`, `cap_unavailable`). Quiet hours are checked BEFORE the reservation (the check is pure), so a held text takes neither a claim nor a slot. A reservation that hits contention is retried in place up to 3 times with jitter (the confirmation too, before it writes its note); if it still cannot commit, the reminder step answers **503 with no claim taken** so QStash delivers it again. The email in the same step does not wait for that: it goes first (its own claim stops the redelivery repeating it) and the 503 is answered last. On QStash's last delivery (`upstash-retried` at the 3 retries every reminder publish asks for) the text is noted on the timeline instead, and the answer is 200. The confirmation, which nobody redelivers, is noted at once. If a window boundary is crossed between the check and the send, the reservation is released; if the release fails it is retried, then the claim is marked `held` (a retry takes it over without counting it twice). If even that fails it is still a hold: the step republishes as for any hold, and the republished step (attempt n) claims its own `sms_{offset}_{token}_a{n}`, so the orphaned claim of the first pass cannot block it. The constants are in `sms-caps.ts`; there is no per-workspace setting.
- **Sender and consent.** Every text goes through `sendSmsForSubAccount` with `origin: "automated"`: the sub-account's own Twilio number, else the shared sender when `agencyAllowsSharedSms`. The auth token is read only through `readSubAccountSecret`. A contact who replied STOP or declined consent (`smsSendBlock`), has no phone, or belongs to another sub-account (`loadEventContact`) gets nothing and nothing is written for them. A carrier 21610 is recorded as `smsOptedOut`.
- **Thread rows only in dedicated mode.** The `contacts/{id}/messages` row and inbox entry are written only for the sub-account's own number (replies route back to us); a shared-sender text writes just the timeline row.
- **Quiet hours.** The confirmation of the customer's own booking (book route) passes `selfTriggeredBookingAt`, so it is exempt for 10 minutes (`quiet-hours.ts`). A reminder held by quiet hours is NOT sent late: its claim is released and the reminder step is published again for the end of the window (`smsOnly`, so the email is not repeated); the republished step re-checks status, token, opt-out and the page's toggle. If the window ends at or after the appointment's start, the reminder is dropped with a timeline note. The mark-paid confirmation is not the customer's own booking, so quiet hours drop it, with a timeline note; the mark-paid email still goes.
- **Live toggles.** The step reads the page's current `remindersEnabled` / `smsRemindersEnabled`, so switching a channel off stops reminders already scheduled; the snapshot in the callback (`channels`) is used only when the page was deleted.
- **Consent line.** The public payload carries one boolean, `textsBooker` (the page's `smsRemindersEnabled`; never the reminder settings). When true, the booking form shows "We'll text booking confirmations and reminders to this number." under the phone field.
- **One reminder text per event per half hour.** Reminders that fire together are the same message twice: a held 720-minute reminder released at 06:00 and the 60-minute one firing at 06:00, or two held to the same window end. Each reminder text first takes `events/{id}/reminderSends/smsrecent_{tokenHash}` (`lib/booking/sms-text-lock.ts`), created in state `sending` and marked `sent` after the text goes. A lock `sent` by another offset in the last 30 minutes makes this one collapse (`already_sent`, with a timeline note). A lock `sending` by another offset makes it WAIT (the step answers 503): that text may still fail, and then this one must go. On QStash's last delivery a `sending` lock that never resolved is taken as crashed and taken over. This offset's own `sending` lock is a crashed attempt or a twin delivery of this very step; its per-offset claim keeps the send exactly-once. A step that sent nothing (a failed send, a re-hold, an error) deletes its lock, so the customer is not left with none. Reminders more than 30 minutes apart are unaffected; offsets within 30 minutes of each other on one page therefore text only once. Each republish carries an `attempt` counter; the QStash dedup id ends `_qh{untilMs}_a{attempt}`, so a re-hold is never collapsed into the first publish while a redelivery of the same step still is.
- **After the response.** The book route's confirmation text runs under `runAfterResponse`, after the reminders are scheduled, the activity row and the booking triggers. The self-trigger exemption is counted from the booking time (10 minutes), not from when the text runs. A confirmation that quiet hours still hold is dropped with a timeline note.
- **Timeline notes.** A text that was not sent leaves a `note_added` row on the (tenant-checked) contact, with a stable id from the claim so a redelivery adds one: no phone, number refused, no sender, send failed, carrier STOP, a daily cap. Not noted: consent (`opted_out`) and a redelivery. Logged Twilio errors have digit runs masked.
- **Not sent:** unpaid holds at booking (their text goes at mark-paid), bookings made by the AI voice agent, and **anything on an agent-approved mark-paid** (no confirmation text and no text reminders: the approver reviews the email address, not the phone; the reminder snapshot carries `sms:false`, which the step honours over the live page, and the `mark_booking_paid` preview says so), a withheld confirmation. The veto is stored on the event (`smsVetoedAt`, server-set, locked in `firestore.rules`), so a later reschedule by the booker or an operator schedules email only and the step refuses to text the event whatever the snapshot says. No WhatsApp variant.
- **NOT runtime-verified.** Tested against the real sender over an in-memory Firestore with the carrier stubbed; no real text was sent, and #1000 has no SMS sender to walk it on. Merges dark: the toggle defaults off.

## Send flow

1. **Public page** (`/b/[subAccountId]/[slug]`) — server-renders the page config; the client fetches slots from the availability endpoint below.
2. **POST `/api/booking/[saId]/[slug]/availability`** — recipient-facing availability re-check (per-IP rate-limited). Used by the date picker when the visitor lands.
3. **POST `/api/booking/[saId]/[slug]/book`** — the actual booking transaction. Validates the inbound payload, re-verifies the slot is still free, reconciles a Contact via `lib/booking/contact-reconcile.ts` (email-first match, falls back to phone, otherwise creates a `source: "booking"` Contact), mints the Event, and triggers the lifecycle pipeline.
4. **Confirmation email** (`lib/booking/email.ts` + `lib/booking/ics.ts`) — sends through the sub-account's verified sending domain via `tenantFrom(sub)`. The ICS attachment uses a stable uid per event so updates chain in Gmail/Outlook: `METHOD:REQUEST` on book (SEQUENCE 0), mark-paid and every reschedule, each with a higher SEQUENCE (`event.icsSequence`, written in the same transaction as the change). **Cancellation sends no ICS** — the cancel emails carry no `METHOD:CANCEL`, so the visitor removes the calendar entry by hand.

## Reschedule + cancel

- `/api/events/[token]/reschedule` and `/api/events/[token]/cancel` — anonymous endpoints, token IS the credential. Each transactionally moves or kills the event, re-mints the ICS uid, and fires the matching lifecycle email + activity entry.
- `/api/events/[token]/cancel` is idempotent: a repeat cancel (or one on a booking already cancelled another way) answers 200 and runs no email, workflow or webhook.
- **One service for both** — [src/lib/server/booking-changes-service.ts](../../src/lib/server/booking-changes-service.ts): `cancelBooking` / `rescheduleBooking` take a `guard(event)` that runs INSIDE the transaction against the live event and decides who may act (the token routes: "this token is the event's live link"; the AI agent, later: "the conversation's contact owns it"). A refusal is `invalid` (the routes answer 404) with nothing written and no token rotated; an imported Google event is refused whatever the guard says. `rescheduleBooking` with `newEnd: null` keeps the booking's own length. Every reschedule — visitor and operator (`rescheduleBookingAsOperator`) — stamps `isLong` with the new times and runs `runRescheduleSideEffects`; side effects are awaited, not deferred.
- `/api/events/reminder/step` — QStash callback for each configured reminder offset. Pulls the live event (so a reschedule cancels stale reminders), checks the booking page's `reminderOffsetMinutes[]`, and sends if still valid, by email and/or text per the page's live toggles ([text reminders](#text-confirmation-and-reminders-port-10-54-b3)). Each reminder is claimed once (`events/{id}/reminderSends`) so a redelivery doesn't send twice; a send failure a retry could fix releases the claim and answers 503 so QStash retries.
- **Operator reschedule** — `POST /api/events/by-id/[id]/reschedule` (member-authenticated) moves a booking-page event's time through `rescheduleBookingAsOperator` (booking-changes-service), i.e. [src/lib/booking/reschedule.ts](../../src/lib/booking/reschedule.ts)'s `rescheduleWithoutAvailabilityCheck` + `runRescheduleSideEffects` — the identical stamps/trigger/reminder-reschedule/visitor-email bookkeeping as the public token endpoint, minus the availability re-check (an operator is trusted to have picked a sane time, same as GHL). Refused with `409` unless the booking still holds a slot (`scheduled`/`awaiting_payment`) and its booking page still exists, and with `400 no_change` when the time is unchanged — none of which rotates the token. The response carries `notifyEmailSent` + `notifyEmailSkipReason` (same vocabulary as mark-status) because the token rotation kills the visitor's old manage link: if the "Updated:" email didn't go out, the dialog says so. The calendar event dialog routes a changed time on a booking-page event through this endpoint *before* writing any other field, so a refused reschedule saves nothing; the time inputs are disabled on cancelled/completed/no-show bookings. Booking-page events are not exposed on the v1 API (see [public-api.md](public-api.md)).
- **Two fixes found proving this end to end (SP3 widget spec):** `/api/events/[token]/reschedule` and `/cancel` were missing from middleware's `PUBLIC_PATH_PATTERNS` (only `/pay` had an entry) — a logged-out visitor's click on either button 307'd to `/login` instead of taking effect. And `PublicEventView` read the manage token off the immutable server-rendered `props.token` instead of state, so a reschedule (which rotates the token) followed by a cancel in the same tab 404'd as "Invalid link" against the now-stale token. Both fixed; both now covered by `e2e/specs/booking-widget.spec.ts`.

## Embeddable widget

A booking page can be dropped into any third-party website as an iframe widget — the same public booking flow as `/b/[subAccountId]/[slug]`, framed.

- **Route:** `/embed/booking/[subAccountId]/[slug]` — server-renders like `/b` (published pages only, same 404-on-draft gate) but mounts `PublicBookingView` with `embedded` set: no full-viewport chrome (the loader sizes the iframe to fit), and the confirmation panel's post-booking redirect targets `window.top` instead of the iframe. `next.config.ts` sends `Content-Security-Policy: frame-ancestors *` on the whole `/embed/:path*` prefix (shared with the web-chat embed), and it's in middleware's `PUBLIC_PATHS`.
- **Loader:** `public/booking-embed.js` — a `widget.js`-style vanilla script. Finds every `<div data-leadstack-booking="<subAccountId>/<slug>">` placeholder (the ref must match `^[A-Za-z0-9_-]+/[A-Za-z0-9_-]+$` — no path traversal), replaces it with an iframe pointed at the embed route, and listens for `postMessage({source:"leadstack-booking-embed", type:"resize", height}, "*")` from that SAME iframe's own `contentWindow` on the app's own origin, resizing the iframe to match. It's a static asset — `PUBLIC_PATHS` carries `/booking-embed.js` separately from `/embed`.
- **Embed dialog:** the booking page detail screen (`/sa/[subAccountId]/booking/[slug]`) has an **Embed** button — disabled with a tooltip on a draft page, same pattern as **Copy link** — opening a dialog with two copy-able snippets: the script+div (auto-resizing, recommended) and a plain fixed-height `<iframe>` fallback.
- **Post-booking redirect:** per the HTML "allowed to navigate" algorithm (enforced by Chrome), a cross-origin iframe can only navigate the top browsing context with a live user gesture — an unattended `setTimeout` has none. So the embedded confirmation panel skips the plain page's timed auto-redirect and shows an immediate **Continue →** link (`target="_top"`) instead; the plain `/b` page's countdown auto-redirect is unaffected (it's a same-window navigation there, not cross-frame).
- **Not done:** no per-page allowed-origin list (any site can embed a published page, same as GHL's calendar embed codes) and the resize `postMessage` target origin is deliberately `"*"` — the payload carries only a height number.

## Paid-booking flow

Pages with `priceCents > 0` mint a `holdUntil` window on the event at book time. The recipient sees a "Pay to confirm" CTA → PayPal.me link (reuses Products + Invoices' `lib/paypal/payment-link.ts`). An operator clicks **Mark paid** in the dashboard to flip the event to confirmed. With Stripe connected, a card deposit (`/api/events/[token]/pay`) does the same from the webhook; its Checkout session expires with the hold (clamped to Stripe's 30 min – 24 h), and mark-paid is a compare-and-set on `awaiting_payment`, so it cannot revive a booking the expiry cancelled (a deposit that lands then is flagged on `order.attention` for a refund), and a webhook racing the button confirms once. Confirming rotates the token; Stripe's return to the pre-payment token (`/e/{token}?paid=1`) shows a read-only "Payment received" page (`paidFromTokenHash`) — the manage link is in the confirmation email. `/api/events/payment/expire-step` is a QStash callback that auto-cancels the hold when `holdUntil` lapses without payment — same lifecycle email path as a manual cancel, just with a `paymentExpired` reason. The assistant's `find_awaiting_payment_bookings` (chat and API agents, territory-scoped) lists held bookings; `mark_booking_paid` ([capabilities/booking-payments.ts](../../src/lib/ai-suite/capabilities/booking-payments.ts)) is API-agent only behind the `outbound` approval and refused in chat (it emails the customer). Its preview pins the contact, the confirmation's recipient, the reminders and the `booking.confirmed` workflows; approve passes them to `markBookingPaidServerSide` as `expect`, so a contact re-linked inside the transaction refuses (`contact_changed`), a changed recipient gets no confirmation (`emailWithheld`), and only the reviewed workflows start, steps unchanged.

## Lifecycle side-effects

[src/lib/booking/lifecycle.ts](../../src/lib/booking/lifecycle.ts) is the single helper that every state-changing booking route calls. It:
1. Writes a typed activity row to `contacts/{contactId}/activities` (`booking_page_booked`, `booking_payment_received`, `booking_cancelled`, `booking_rescheduled`, `booking_no_show`, `booking_completed`).
2. Dispatches into `fireBookingTrigger()`, which maps the (legacy-named) `event_*` trigger literal to the matching Workflow Builder `booking.*` trigger type — `event_booked→booking.created`, `event_cancelled→booking.cancelled`, `event_rescheduled→booking.rescheduled`, `event_paid`/`event_confirmed→booking.confirmed`, `event_completed→booking.showed`, `event_no_show→booking.no_show` — and always passes `{eventId, bookingPageSlug}` as trigger context so a workflow can pin itself to one booking page (see [docs/features/workflows.md](workflows.md)).
3. Returns the lifecycle outcome so the calling route can include it in the response body.

## Status lifecycle

`EventStatus` is unchanged (`scheduled | awaiting_payment | completed | cancelled | no_show`); only the operator-facing labels use GHL's vocabulary, via the single `eventStatusLabel()` helper in [src/types/events.ts](../../src/types/events.ts): `scheduled` → **Confirmed**, `awaiting_payment` → **Unconfirmed (awaiting payment)**, `completed` → **Showed**, `no_show` → **No-show**, `cancelled` → **Cancelled**.

`POST /api/events/by-id/[id]/mark-status` (and the v1 API's `status` PATCH, via the shared [src/lib/server/event-status-service.ts](../../src/lib/server/event-status-service.ts)) allows: `scheduled` → `completed`/`no_show`/`cancelled`; `completed` ↔ `no_show` as a correction either direction (re-fires the matching `booking.showed`/`booking.no_show` trigger each time); `cancelled` is always final. `awaiting_payment` only exits via mark-paid. `completed`/`no_show` additionally require the event's `startAt` to already be in the past — refused with "This appointment hasn't happened yet." otherwise, so a future booking can't be flipped (and its trigger fired, freeing the slot) before it actually happens; `cancelled` has no such requirement.

**Decision: mark-status applies identically to manual (non-booking-page) calendar events with a linked contact.** There is no separate code path — a manual event's `bookingPageSlug` is `null`, so it fires `booking.showed`/`booking.no_show`/`booking.cancelled` with `bookingPageSlug: null` in the trigger context, which a page-filtered workflow never matches (only an unfiltered one fires). This was a deliberate scope decision, not an oversight.

## Google Calendar sync

When the agency enables `googleCalendarEnabledByAgency`, each host can connect their own Google Calendar: their Google busy time blocks their slots (availability, book, reschedule and voice all read it, fail open), and every booking assigned to them is pushed to their primary calendar after book / reschedule / cancel / payment expiry / mark-paid / reassign. Hostless pages are unaffected. See [Google Calendar sync](google-calendar-sync.md).

## Setup contract

**No new env vars.** Reuses `RESEND_API_KEY` + `EMAIL_FROM` (confirmations), `AUTOMATIONS_TOKEN_SECRET` (HMAC for the public reschedule/cancel tokens), `QSTASH_*` (reminder + payment-expiry schedules), `NEXT_PUBLIC_APP_URL` (public URL construction). Booking pages are public so `/b` + `/api/booking` are in middleware's `PUBLIC_PATHS`. Reuses the per-sub-account dedicated sending domain when configured — confirmation emails go out from the tenant brand.
