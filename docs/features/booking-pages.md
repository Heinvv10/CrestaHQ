# Booking pages v1

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

Native Calendly-style slot picker per sub-account. The operator configures a Booking Page (durations, working hours, optional price, optional reminder offsets) and shares the public URL `/b/[subAccountId]/[slug]`. A visitor picks a slot, the server transactionally re-verifies availability, reconciles a Contact, mints an Event, and sends an ICS-attached confirmation email. Reschedule + cancel + reminders + payment-expiry are all queued through QStash so they keep firing across Vercel cold starts.

## Data model

- `subAccounts/{id}/bookingPages/{pageId}` — page config (slug, timezone, duration, padding, working hours, required fields, optional `priceCents`, optional `reminderOffsetMinutes[]`, `status: "draft" | "published"`).
- `subAccountDoc.bookingLink` — the sub-account's **default booking link**: the URL the `{{bookingLink}}` merge tag resolves (workflows, broadcasts, WhatsApp templates, review requests) AND the link the AI agents share when someone wants to book (`buildSystemPrompt`'s channel-aware booking block — text channels share the URL, voice promises it by text). Set by admins via the **Default booking link** card on the Booking page ([src/components/booking/default-booking-link-card.tsx](../../src/components/booking/default-booking-link-card.tsx)) — pick a published booking page or paste a custom URL (Calendly etc.); saves through the existing sub-account PATCH. (The original setter died with the legacy Automations → Settings page — until this card, the tag silently resolved to "".)
- `events/{eventId}` — the existing Calendar events collection picks up two new optional fields: `bookingPageId` (denormalised back-reference) + `bookingMeta` (the recipient-typed payload + ICS uid).
- Token: bookings mint a public `bookingEventToken` HMAC-signed via `AUTOMATIONS_TOKEN_SECRET`, used in confirmation-email links so the recipient can reschedule or cancel without a login. The raw token never persists — only the SHA-256 hash on the event doc.

## Calendar types (SP3)

A page's `calendarType` (absent on legacy pages ⇒ `pageCalendarType()` derives `round_robin` when it has hosts, else `personal`):

| Type | Slots | Booking |
|---|---|---|
| `personal` | One host: that host's events + unassigned events block. No host: every event in the sub-account blocks (legacy single schedule) | Stamps the host |
| `round_robin` | Union of each host's free time | One host: `distribution` `equal` (least loaded, then `priority`) or `availability` (priority, then load); page order last |
| `collective` | Intersection — every host free (each host's own hours) | Every host: `hostUids[]`, `assignedToUid` = first. Blocks each listed host everywhere |
| `class` | Same-page bookings at the slot start are seats (`seatsPerSlot` ≥2); the day cap counts booked sessions (start instants) | One event per attendee. A hostless class page's seats carry no host, so each one is shared busy — it blocks every host's other pages for that time |
| `service` | Sized to the picked service (`services[]`, 1–20) | As round robin; stamps `serviceId`/`serviceName` |

Every caller that offers or re-verifies a slot — availability API, book route and reschedule route (inside their transactions), voice agent — goes through `resolvePageAvailability` ([src/lib/booking/resolve-availability.ts](../../src/lib/booking/resolve-availability.ts)); the rules are pure in [page-slots.ts](../../src/lib/booking/page-slots.ts). Reschedule re-verifies the event as it was booked (`MovingEvent`): all of its own host(s) — one no longer on the page keeps the page hours while still an active member, and is refused with a 409 ("… is no longer available — please contact the business to rebook") once they are not — its service, or its own length when that service is gone. A hostless booking on a page that has since gained hosts keeps the legacy shared schedule (every event blocks). The reschedule view's `excludeEventId` is honoured only for an event booked on that page. Voice refuses service pages (no service step on a call).

**Rollout:** the host readers (per-host `.ics` feed, round-robin load, reassign conflict check) query `events(subAccountId, hostUids CONTAINS, startAt)` through `queryHostEvents`. Deploy `firestore.indexes.json` and let that index finish building BEFORE shipping this code; until it does, the collective half of each read fails (logged) and only owned bookings are seen.

## Availability rules (SP3)

All optional; absent ⇒ the old behaviour. Applied in [page-slots.ts](../../src/lib/booking/page-slots.ts) / [availability.ts](../../src/lib/booking/availability.ts), so every caller of the resolver gets them.

- **Date-specific hours** — `dateOverrides[]` (`{date: "YYYY-MM-DD", ranges}`, page timezone) on the page and per host. Empty `ranges` = closed that date; an entry can also open a date the weekly hours leave closed. Precedence for one host on one date: a page entry that **closes** the date closes it for everyone; otherwise the host's own entry wins; otherwise a page entry that changes hours applies — but only to hosts on the page hours (a host with custom weekly hours keeps them); otherwise weekly hours. Max 366 per list; past dates are kept.
- **Buffers** — `bufferBeforeMinutes` (new) and `bufferMinutes` (now the *after* buffer). A new slot `[S, E)` must have `[S − before, E + after)` clear of every busy interval (manual events, other pages' bookings, external busy). This page's own bookings also keep their buffers, so two bookings on the same page are at least `max(before, after)` apart.
- **Slot interval** — `slotIntervalMinutes` (5–240, step 5): minutes between slot starts, across services too. Null ⇒ `durationMinutes + bufferMinutes`, the old step.
- **Max per day** — `maxPerDay` caps the BOOKINGS the page holds on a local date (per host on pages with hosts; booked sessions on class pages) — [day-cap.ts](../../src/lib/booking/day-cap.ts). Every status but cancelled counts: a completed or no-show booking still used the day. A date at the cap offers nothing more, and the book/reschedule re-verify refuses it. It used to cap the free slots *offered* (first N shown), which limited nothing.
- **Long busy events** — the main busy read ranges on `startAt` and looks back 26 h. Events longer than 8 h (a multi-day "Out of office") carry `isLong: true`, written by every path that sets an event's times ([long-event.ts](../../src/lib/booking/long-event.ts); booking and voice bookings are slot-sized and leave it absent), and a second query on `(subAccountId, isLong, startAt)` finds those that began up to 366 days earlier. That query runs outside the book/reschedule transaction (bookings are never long, so it needs no conflict detection) and **fails soft** — no long events, logged once — while its index is missing.
  **Rollout (owner-gated):** deploy `firestore.indexes.json` and wait for the index, deploy the app, then run `node --env-file=.env.local --experimental-strip-types scripts/backfill-event-is-long.ts --project <id>` (dry run) and again with `--apply`. Until then long events that began more than 26 h before a slot are not seen — no worse than before, when the read looked back 8 h.

**Behaviour change for existing pages:** before SP3 `bufferMinutes` was only the slot step and never padded existing events — a 15-min buffer still allowed a slot starting right when a manual event ended. It now pads busy time as the after-buffer. Slots next to the page's own on-grid bookings are unchanged (the step already leaves that gap); a slot whose after-buffer runs into an off-grid manual event, or a same-page booking closer than the buffer, is no longer offered.

## Style presets (shared with checkout pages)

Five presets — Clean, Midnight, Noir Lime, Sunset, Ocean — restyle the public booking page (`/b`, and the embed) and the public checkout page (`/co`). One table, [src/lib/checkout/themes.ts](../../src/lib/checkout/themes.ts), holds every value; the ids in `CHECKOUT_THEME_IDS` ([src/types/checkout-pages.ts](../../src/types/checkout-pages.ts)) are stored on the page doc as `themePreset` and are append-only. Both editors use the same picker ([src/components/checkout/theme-preset-picker.tsx](../../src/components/checkout/theme-preset-picker.tsx)). *Ported from upstream 1.0.40; not yet walked in a browser as of 2026-10-11.*

- **A preset is style only.** Content and layout are the same with or without one. Nothing a tenant types reaches a `style` or `class` attribute through a preset: the stored value is only ever compared against the id list, and the styles come from the table.
- **No preset = the look the page always had.** `themePreset` null, absent, or an id this build does not know all mean "no preset". On `/b` that is the app's own tokens plus the page's optional `accentColor`, with no added markup. On `/co` it is `legacyCheckoutTheme()`: the exact values the page hard-coded before presets, pinned byte for byte by [src/test/checkout-legacy-markup.json](../../src/test/checkout-legacy-markup.json) (captured at the commit before presets; do not regenerate it to make a test pass).
- **Booking:** the preset is applied by setting the shadcn CSS variables inline on `<main>` (plus the `dark` class for dark presets), so every `bg-card` / `text-muted-foreground` underneath follows. A page's own `accentColor` still wins over the preset's accent. "Brand default" in the picker clears the preset. `/e/[token]` (reschedule/cancel) is not themed.
- **Checkout:** a new page starts on Clean. A page saved before presets shows "Brand default" in the editor and keeps no preset until one is picked, so saving another field never restyles it; once a preset is saved the page's own `appearance.accent` no longer applies.
- **Writes:** an unknown id is refused with "Unknown style preset." by `validateThemePreset` (booking routes and the agent's `create_booking_page` / `update_booking_page`) and by `sanitizeCheckoutPagePayload` (checkout routes).

## Send flow

1. **Public page** (`/b/[subAccountId]/[slug]`) — server-renders the page config; the client fetches slots from the availability endpoint below.
2. **POST `/api/booking/[saId]/[slug]/availability`** — recipient-facing availability re-check (per-IP rate-limited). Used by the date picker when the visitor lands.
3. **POST `/api/booking/[saId]/[slug]/book`** — the actual booking transaction. Validates the inbound payload, re-verifies the slot is still free, reconciles a Contact via `lib/booking/contact-reconcile.ts` (email-first match, falls back to phone, otherwise creates a `source: "booking"` Contact), mints the Event, and triggers the lifecycle pipeline.
4. **Confirmation email** (`lib/booking/email.ts` + `lib/booking/ics.ts`) — sends through the sub-account's verified sending domain via `tenantFrom(sub)`. The ICS attachment uses a stable uid per event so updates chain in Gmail/Outlook: `METHOD:REQUEST` on book (SEQUENCE 0), mark-paid and every reschedule, each with a higher SEQUENCE (`event.icsSequence`, written in the same transaction as the change). **Cancellation sends no ICS** — the cancel emails carry no `METHOD:CANCEL`, so the visitor removes the calendar entry by hand.

## Reschedule + cancel

- `/api/events/[token]/reschedule` and `/api/events/[token]/cancel` — anonymous endpoints, token IS the credential. Each transactionally moves or kills the event, re-mints the ICS uid, and fires the matching lifecycle email + activity entry.
- `/api/events/[token]/cancel` is idempotent: a repeat cancel (or one on a booking already cancelled another way) answers 200 and runs no email, workflow or webhook.
- `/api/events/reminder/step` — QStash callback for each configured reminder offset. Pulls the live event (so a reschedule cancels stale reminders), checks the booking page's `reminderOffsetMinutes[]`, and sends if still valid. Each reminder is claimed once (`events/{id}/reminderSends`) so a redelivery doesn't send twice; a send failure a retry could fix releases the claim and answers 503 so QStash retries.
- **Operator reschedule** — `POST /api/events/by-id/[id]/reschedule` (member-authenticated) moves a booking-page event's time through [src/lib/booking/reschedule.ts](../../src/lib/booking/reschedule.ts)'s `rescheduleWithoutAvailabilityCheck` + `runRescheduleSideEffects` — the identical stamps/trigger/reminder-reschedule/visitor-email bookkeeping as the public token endpoint, minus the availability re-check (an operator is trusted to have picked a sane time, same as GHL). Refused with `409` unless the booking still holds a slot (`scheduled`/`awaiting_payment`) and its booking page still exists, and with `400 no_change` when the time is unchanged — none of which rotates the token. The response carries `notifyEmailSent` + `notifyEmailSkipReason` (same vocabulary as mark-status) because the token rotation kills the visitor's old manage link: if the "Updated:" email didn't go out, the dialog says so. The calendar event dialog routes a changed time on a booking-page event through this endpoint *before* writing any other field, so a refused reschedule saves nothing; the time inputs are disabled on cancelled/completed/no-show bookings. Booking-page events are not exposed on the v1 API (see [public-api.md](public-api.md)).
- **Two fixes found proving this end to end (SP3 widget spec):** `/api/events/[token]/reschedule` and `/cancel` were missing from middleware's `PUBLIC_PATH_PATTERNS` (only `/pay` had an entry) — a logged-out visitor's click on either button 307'd to `/login` instead of taking effect. And `PublicEventView` read the manage token off the immutable server-rendered `props.token` instead of state, so a reschedule (which rotates the token) followed by a cancel in the same tab 404'd as "Invalid link" against the now-stale token. Both fixed; both now covered by `e2e/specs/booking-widget.spec.ts`.

## Embeddable widget

A booking page can be dropped into any third-party website as an iframe widget — the same public booking flow as `/b/[subAccountId]/[slug]`, framed.

- **Route:** `/embed/booking/[subAccountId]/[slug]` — server-renders like `/b` (published pages only, same 404-on-draft gate) but mounts `PublicBookingView` with `embedded` set: no full-viewport chrome (the loader sizes the iframe to fit), and the confirmation panel's post-booking redirect targets `window.top` instead of the iframe. `next.config.ts` sends `Content-Security-Policy: frame-ancestors *` on the whole `/embed/:path*` prefix (shared with the web-chat embed), and it's in middleware's `PUBLIC_PATHS`.
- **Loader:** `public/booking-embed.js` — a `widget.js`-style vanilla script. Finds every `<div data-leadstack-booking="<subAccountId>/<slug>">` placeholder (the ref must match `^[A-Za-z0-9_-]+/[A-Za-z0-9_-]+$` — no path traversal), replaces it with an iframe pointed at the embed route, and listens for `postMessage({source:"leadstack-booking-embed", type:"resize", height}, "*")` from that SAME iframe's own `contentWindow` on the app's own origin, resizing the iframe to match. It's a static asset — `PUBLIC_PATHS` carries `/booking-embed.js` separately from `/embed`.
- **Embed dialog:** the booking page detail screen (`/sa/[subAccountId]/booking/[slug]`) has an **Embed** button — disabled with a tooltip on a draft page, same pattern as **Copy link** — opening a dialog with two copy-able snippets: the script+div (auto-resizing, recommended) and a plain fixed-height `<iframe>` fallback.
- **Post-booking redirect:** per the HTML "allowed to navigate" algorithm (enforced by Chrome), a cross-origin iframe can only navigate the top browsing context with a live user gesture — an unattended `setTimeout` has none. So the embedded confirmation panel skips the plain page's timed auto-redirect and shows an immediate **Continue →** link (`target="_top"`) instead; the plain `/b` page's countdown auto-redirect is unaffected (it's a same-window navigation there, not cross-frame).
- **Not done:** no per-page allowed-origin list (any site can embed a published page, same as GHL's calendar embed codes) and the resize `postMessage` target origin is deliberately `"*"` — the payload carries only a height number.

## Paid-booking flow

Pages with `priceCents > 0` mint a `holdUntil` window on the event at book time. The recipient sees a "Pay to confirm" CTA → PayPal.me link (reuses Products + Invoices' `lib/paypal/payment-link.ts`). An operator clicks **Mark paid** in the dashboard to flip the event to confirmed. With Stripe connected, a card deposit (`/api/events/[token]/pay`) does the same from the webhook; its Checkout session expires with the hold (clamped to Stripe's 30 min – 24 h), and mark-paid is a compare-and-set on `awaiting_payment`, so it cannot revive a booking the expiry cancelled (a deposit that lands then is flagged on `order.attention` for a refund), and a webhook racing the button confirms once. Confirming rotates the token; Stripe's return to the pre-payment token (`/e/{token}?paid=1`) shows a read-only "Payment received" page (`paidFromTokenHash`) — the manage link is in the confirmation email. `/api/events/payment/expire-step` is a QStash callback that auto-cancels the hold when `holdUntil` lapses without payment — same lifecycle email path as a manual cancel, just with a `paymentExpired` reason.

## Lifecycle side-effects

[src/lib/booking/lifecycle.ts](../../src/lib/booking/lifecycle.ts) is the single helper that every state-changing booking route calls. It:
1. Writes a typed activity row to `contacts/{contactId}/activities` (`booking_page_booked`, `booking_payment_received`, `booking_cancelled`, `booking_rescheduled`, `booking_no_show`, `booking_completed`).
2. Dispatches into `fireBookingTrigger()`, which maps the (legacy-named) `event_*` trigger literal to the matching Workflow Builder `booking.*` trigger type — `event_booked→booking.created`, `event_cancelled→booking.cancelled`, `event_rescheduled→booking.rescheduled`, `event_paid`/`event_confirmed→booking.confirmed`, `event_completed→booking.showed`, `event_no_show→booking.no_show` — and always passes `{eventId, bookingPageSlug}` as trigger context so a workflow can pin itself to one booking page (see [docs/features/workflows.md](workflows.md)).
3. Returns the lifecycle outcome so the calling route can include it in the response body.

## Status lifecycle

`EventStatus` is unchanged (`scheduled | awaiting_payment | completed | cancelled | no_show`); only the operator-facing labels use GHL's vocabulary, via the single `eventStatusLabel()` helper in [src/types/events.ts](../../src/types/events.ts): `scheduled` → **Confirmed**, `awaiting_payment` → **Unconfirmed (awaiting payment)**, `completed` → **Showed**, `no_show` → **No-show**, `cancelled` → **Cancelled**.

`POST /api/events/by-id/[id]/mark-status` (and the v1 API's `status` PATCH, via the shared [src/lib/server/event-status-service.ts](../../src/lib/server/event-status-service.ts)) allows: `scheduled` → `completed`/`no_show`/`cancelled`; `completed` ↔ `no_show` as a correction either direction (re-fires the matching `booking.showed`/`booking.no_show` trigger each time); `cancelled` is always final. `awaiting_payment` only exits via mark-paid. `completed`/`no_show` additionally require the event's `startAt` to already be in the past — refused with "This appointment hasn't happened yet." otherwise, so a future booking can't be flipped (and its trigger fired, freeing the slot) before it actually happens; `cancelled` has no such requirement.

**Decision: mark-status applies identically to manual (non-booking-page) calendar events with a linked contact.** There is no separate code path — a manual event's `bookingPageSlug` is `null`, so it fires `booking.showed`/`booking.no_show`/`booking.cancelled` with `bookingPageSlug: null` in the trigger context, which a page-filtered workflow never matches (only an unfiltered one fires). This was a deliberate scope decision, not an oversight.

## Google Calendar sync

When the agency enables `googleCalendarEnabledByAgency`, each host can connect their own Google Calendar: their Google busy time blocks their slots (availability, book, reschedule and voice all read it, fail open), and every booking assigned to them is pushed to their primary calendar after book / reschedule / cancel / payment expiry / mark-paid / reassign. Hostless pages are unaffected. See [Google Calendar sync](google-calendar-sync.md).

## Setup contract

**No new env vars.** Reuses `RESEND_API_KEY` + `EMAIL_FROM` (confirmations), `AUTOMATIONS_TOKEN_SECRET` (HMAC for the public reschedule/cancel tokens), `QSTASH_*` (reminder + payment-expiry schedules), `NEXT_PUBLIC_APP_URL` (public URL construction). Booking pages are public so `/b` + `/api/booking` are in middleware's `PUBLIC_PATHS`. Reuses the per-sub-account dedicated sending domain when configured — confirmation emails go out from the tenant brand.
