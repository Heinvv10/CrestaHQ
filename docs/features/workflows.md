# Workflow Builder (v1 + v2)

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

The general automation engine + visual builder at `/sa/[id]/workflows` (it replaced the legacy single-recipe `automations` engine — those files are gone; Speed-to-Lead lives on as a starter template). A workflow = a **trigger** + a graph of **nodes** (linear steps with two-way branches); each contact enrollment is a `workflowRuns/{runId}` doc advanced node-by-node by the QStash step worker.

- **Triggers (18)** — `contact.created`, `contact.tag.added` (optional per-tag filter `trigger.tag`: start only when THAT tag is among the ones the write added — without it the workflow starts on any new tag, and a `has_tag` filter alone re-enrols a contact who already carries the tag whenever some other tag arrives), `form.submitted` (optional per-form filter), `pipeline.stage.changed` (optional target-stage filter `trigger.toStage` + optional pipeline filter `trigger.pipelineId`; context carries `pipelineId`, `fromStage`, `toStage`, `dealId`), `deal.created`, `deal.won`, `deal.lost` (won/lost = the stage's `terminal` flag on the deal's pipeline; optional `trigger.pipelineId` filter; fired from `lib/server/deals-service.ts` where the matching webhooks fire), `booking.created`, `booking.cancelled`, `booking.rescheduled`, `booking.confirmed` (a free booking-page slot at book time, or a paid hold once the operator marks it paid or the payment is reconciled — never via the v1 API, which does not expose booking-page events), `booking.showed`, `booking.no_show` (operator marks a past booking attended/no-show — a correction, flipping one to the other, re-fires the matching trigger) — every `booking.*` trigger takes an optional per-page filter `trigger.bookingPageSlug` (null/absent = any page; context carries `eventId`, `bookingPageSlug` — a manual, non-booking-page event always has `bookingPageSlug: null` and never matches a page-pinned workflow), `quote.accepted`, `quote.paid` (covers invoices), `message.received` (optional channel filter: sms/whatsapp/messenger/instagram; fired from the unified-inbox upsert). Dispatch: [src/lib/workflows/engine.ts](../../src/lib/workflows/engine.ts)::`fireWorkflowTrigger()` called from the server-side write paths, never from clients. It returns a `TriggerOutcome` — the runs it created (`running`, or `failed` when the first step could not be scheduled) and why each other matching-type workflow was skipped (`trigger_mismatch`, `filters_not_met`, `reentry_blocked`, `no_start_node`). Nearly every caller discards it; the v1 contact upsert awaits it to answer its caller.
- **Nodes (14)** — send_email, send_sms, whatsapp_template (approved templates only), send_whatsapp (free-form text in the 24h window; its optional template is the closed-window fallback if approved — and if that template has **buttons**, the step sends the template's own text WITH them in-window as a free Cloud interactive message, approved or not: reply buttons for quick replies, `cta_url` for a single link; Meta's in-window limits — 20-character labels, one link, no mixing — refuse the in-window send rather than strip, while outside the window an approved template still goes as itself; on Twilio the buttons go in-session as an unapproved Content resource created once per template and cached on it; the bridge refuses in-window buttons until its button PRs), wait, **wait_for_reply** (v2 — see below), if_else, goal (end), add_tag, remove_tag, move_stage (writes `contact.pipelineStage`; with a pipeline chosen it also moves the contact's most recently updated open deal in that pipeline through `updateDealServerSide`, so webhooks and the `pipeline.stage.changed` trigger fire as for a manual move — capped at 5 chained workflow-made moves), update_field (allowlisted fields + customFields.*), create_task (optional assignee, honoured only while an active member at run time), notify (owner/account-contact/custom), webhook (POSTs contact + form fields to any URL). Registry in `engine.ts`; labels/config-shapes in [src/lib/workflows/catalog.ts](../../src/lib/workflows/catalog.ts).
- **wait_for_reply (v2)** — a branching node: "wait up to N for the contact's next inbound message". Arm phase parks the run (`run.waiting`, status `waiting`) and schedules a same-node QStash timeout callback carrying `phase: "timeout"`; the unified-inbox upsert ([src/lib/server/conversations-service.ts](../../src/lib/server/conversations-service.ts)) resolves parked runs early via `resumeWaitingRunsOnReply()`. Both paths claim the node in a transaction (re-checking `waiting` + history), so exactly one of Replied/No-reply wins; the winner's history entry makes the loser's callback a no-op via the step worker's idempotency guard. A WhatsApp **button tap is a reply**: the Cloud and Twilio webhooks put the tapped button's text in the message body, so it resumes the wait and an `if_else` can branch on `reply.text` (e.g. equals "Yes, all good"); the button's payload/id is kept on the message row as `buttonPayload`. A tap that resumes NO waiting run (the wait timed out) flags the conversation `lateButtonTap` — a **Late tap** badge in the inbox — and never resumes the finished run; a human reply clears it. Detects SMS/WhatsApp/Messenger/Instagram only — **email replies bypass the app by design** (Reply-To → operator's inbox) and the builder says so on the node.
- **Conditions** — `ConditionGroup = { all: Condition[], match?: "all" | "any" }` ([src/lib/workflows/conditions.ts](../../src/lib/workflows/conditions.ts)); `match` absent = AND (every pre-v2 doc unchanged). Used by trigger filters and if_else. Ops: equals/not_equals/contains/is_set/not_set/has_tag/in_stage/source_is.
- **Re-enrollment (v2)** — `WorkflowDoc.reentry`: `every_time` (default, absent = this) | `unless_active` | `once_ever`, enforced in `fireWorkflowTrigger` via an equality-only `workflowRuns(workflowId, contactId)` query (fails open). Test enrollments bypass. The builder defaults `message.received` templates to `unless_active` — an auto-responder that re-enrolls per message is the classic footgun.
- **Step worker** — `POST /api/workflows/step` (QStash signature-verified, in `PUBLIC_PATH_PATTERNS`). Idempotent on `run.history` (nodeId presence). Sends reuse the shared compliance helpers: opt-out checks per channel, `{{unsubscribeLink}}` in emails, merge tags, `automationsPaused` kill switch checked at dispatch AND per step.
- **Starter templates (5)** — Speed-to-Lead, Appointment Confirmation, Lead Nurture, Stage-Change Follow-up, **No-reply Follow-up** (v2: message.received → wait_for_reply 2d → SMS nudge → wait_for_reply 3d → notify on re-engage / task if still silent; seeds `reentry: "unless_active"`). Seeds in [src/lib/server/workflows-service.ts](../../src/lib/server/workflows-service.ts); the AI assistants can create any of them via the `create_workflow` capability.
- **Folders (W1 1a)** — the list groups workflows by `subAccounts/{id}/workflowFolders/{folderId}` (folder `order`, then name; **Unfiled** last). `WorkflowDoc.folderId` is optional — absent/null, or pointing at a deleted folder, renders Unfiled — and the engine never reads it. Create/rename/delete inline on the list; move via the row's folder menu, which is the `folderId` field of the existing workflow PATCH (a folder id not under this sub-account's path → 404, nothing written). Deleting a folder unfiles its workflows in one transaction and never deletes a workflow. Decisions: [docs/programme/w1-folders.md](../programme/w1-folders.md).
- **Indexes** — none needed for the v2 queries: `(contactId, status)` and `(workflowId, contactId)` are equality-only, served by Firestore index merging (same as the 3-equality dispatch query).
- **Local dev** — QStash needs a public callback URL. Run a cloudflared/ngrok tunnel and set `NEXT_PUBLIC_APP_URL` to it while testing workflows; timed waits + wait_for_reply timeouts won't fire without it.
