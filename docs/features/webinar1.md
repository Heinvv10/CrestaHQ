# Webinar1 integration

*Part of the [LeadStack CRM](../../CLAUDE.md) docs. Feature index: [docs/features](../features/README.md).*

Per-sub-account connection to a self-hosted Webinar1 deployment (the webinar boilerplate, same product family). Greenfield module — do not confuse it with the `/webinar` marketing funnel routes, which SELL LeadStack via webinar1.dev and are unrelated.

- **Secret split (same rule as Payments v1):** `subAccounts/{id}/private/webinar1Connection` holds `{baseUrl, apiKey (wbk_…), webhookSecret (whsec_…), webhookEndpointId}` — Admin SDK only, covered by the generic `private/{docId}` deny rule. Non-secret display metadata is `SubAccountDoc.webinar1ConnectionMeta` (`src/types/webinar1.ts`).
- **Chokepoint:** `src/lib/webinar1/client.ts` is the ONLY reader of the API key. Every call to the remote deployment (`${baseUrl}/api/launchcast/v1/*`, `Authorization: Bearer wbk_…`) goes through `getWebinar1Client(subAccountId)`; it throws typed `Webinar1ConnectionError` rather than returning null.
- **Connect/disconnect:** `/api/sub-accounts/[id]/webinar1-connection` (admin-only). POST probes the credentials (list webinars) before storing, then auto-registers OUR receiver on THEIR deployment via Webinar1's `POST /v1/webhook-endpoints` (returns the signing secret once); failure falls back to a manual `whsec_` paste — same shape as the Stripe connection route. DELETE removes the remote endpoint best-effort. Settings card: `src/components/settings/sub-account-webinar1-section.tsx` (Admin tab).
- **Proxies + push:** `/api/sub-accounts/[id]/webinar1/{webinars,videos}` (member GET; webinar POST is admin-only) and `/api/sub-accounts/[id]/webinar1/register` (member; `{contactId, webinarId}` — refuses contacts with no email or `emailOptedOut`). UI: `/sa/[subAccountId]/webinars` page + "Webinars" sidebar entry.
- **Inbound webhook:** `/api/webhooks/webinar1/sa/[subAccountId]` — in `PUBLIC_PATH_PATTERNS`; verifies `X-Webinar1-Signature` (Stripe-style `t=,v1=` over `${t}.${rawBody}` — the EXACT scheme of our own outbound webhooks, so it reuses `verifyWebhookSignature` from `lib/api/webhooks/signing.ts`). Reconciles the contact by email (single-field equality + in-code tenancy filter, the Meta pattern), creates with `source: "webinar"` when missing, and logs `webinar_registered` / `webinar_joined` / `webinar_completed` / `webinar_cta_clicked` activities. Returns 200 for everything except a bad signature (non-2xx makes Webinar1 retry and eventually auto-disable the endpoint).
- **Idempotency:** activity rows use deterministic doc ids (`<type>_<registrationId>`) written with `create()` + swallowed ALREADY_EXISTS (`src/lib/webinar1/activities.ts`) — delivery retries, repeat CTA clicks, and the CRM-push-then-webhook-echo all collapse into one row with the original timestamp.
- **Agency-gated like Website/Payments:** `webinar1EnabledByAgency` (opt-in, `=== true`; explicit `false` at both creation sites) with `webinar1HiddenWhenDisabled` for the sidebar hide-vs-Locked choice. Standalone `AgencyGateField` (NOT in `PLAN_GATE_KEYS` — an external connection is an explicit per-client decision, same reasoning as Payments; promote if that changes). Wired through the Manage-dialog GateToggle, `/api/agency/sub-accounts/[id]/feature-gates`, the sidebar gate states, a `webinars` entry in `FEATURE_GATES` (ai-suite capabilities), and `lib/webinar1/gate.ts` for the runtime 403s (connection POST + all `/webinar1/*` routes; DELETE disconnect stays ungated for cleanup). The inbound webhook warn-and-drops with 200 while the gate is off so the platform never auto-disables the endpoint; the settings card self-gates; the Webinars page shows a Locked notice on direct URL access.
- **No composite indexes, no new env vars.** Webinar1's API reference lives in that repo at `docs/api.md`.
