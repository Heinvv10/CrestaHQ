## Risks named up front

- **Storage rules cannot read Firestore membership cheaply** — Storage rules support `firestore.get()` (GA since 2024) but each call is billed and adds latency; alternative is custom-claim `subAccountIds`. Decide in (a) after checking what the auth claims carry today (`docs/architecture/auth-and-tenancy.md`).
- **Snapshot import across agencies** breaks the "agency-owner read" model — the imported copy must be re-stamped with the importing `agencyId` and never keep source ids that could dereference into the source agency.
- **Launchpad "real state"** — every item must read the doc the feature itself writes, not a parallel flag, or it drifts the day the feature changes its storage.
- **Template library** duplicates snapshot capture unless the per-entity capture functions are exported and reused — do not fork them.

## Grill rulings (2026-09-15, answered from the code)

1. **Storage authz** — claims are `{role,status,agencyId,agencyRole}` only (no membership list). Storage path is `media/{subAccountId}/{fileId}`; rules pass an agency owner by claims + one `firestore.get()` of the sub-account doc for its `agencyId`, and a member by one `firestore.get()` of `subAccounts/{sa}/subAccountMembers/{uid}` — the same shape `firestore.rules` uses. Uploads are client-direct (progress, no route body cap); "Get Link" is the token download URL, shareable regardless of read rules. Cross-tenant proof: the spec mints a throwaway member of the *secondary* fixture sub-account and reads a *primary* object → 403.
2. **Template library reuses snapshots** — a template is a `SnapshotPayload` with one entity populated; push calls `applySnapshot` unchanged (create-only, drafts). Capture exports `stripDoc` for a single doc. Kinds: `workflow | message_template | form` ("email template" = `MessageTemplateDoc{type:"email"}`).
3. **Launchpad reads real state** from the member-readable parent doc: `emailProvider`/`smtpConfig`/`resendConfig`, `whatsappCloudMeta`/`whatsappBridgeMeta`, `googleConnectionMeta`, plus booking-page / contact / workflow counts. No parallel flags.
4. **Auth helpers** — share create/revoke + templates: `requireAgencyOwner(agencyId)`; import: `requireAgencyOwnerAny` (importing agency from the caller's claims). Cross-agency import is proven with a throwaway agency + owner user the spec creates, signs in via `/login` in a second context, and tears down.
5. **Rules deploy** must include `storage` and may need the Rules→Firestore service-agent grant on first cross-service use — handle at deploy time, not by design change.
