# SP15 — WhatsApp settings: profile, quality rating, message links

**Date:** 2026-09-11 · **Depends on:** SP0 · **Blocks:** SP2 (inbox uses the sender header)
Programme context: [PARITY_PROGRAM.md](../PARITY_PROGRAM.md) §SP15.

GHL's Settings → WhatsApp page is three Meta Graph resources on the connected
phone number: `whatsapp_business_profile` (the Profile tab), the phone-number
node's `quality_rating` / `name_status` / `status` (the header badge), and
`message_qrdls` (the Message Links tab). LeadStack already holds the
system-user token per sub-account; this subproject calls those resources and
puts the same page in front of the operator.

---

## Decision summary (grilled 2026-09-11)

**Verdict:** Proceed with constraints. Grilled against the codebase rather
than Hein — every question below was answerable from files or a read-only
probe, and the 09-11 handoff had already fixed the scope.

### Decided

1. **Page lives at `/sa/[id]/dashboard/settings/whatsapp`, not
   `/sa/[id]/settings/whatsapp`.** Every sub-account settings surface in this
   repo is under `dashboard/settings` (one page, five tabs). A new
   `settings/` segment would be a second settings root. The Messaging tab's
   Cloud card links to the new page. Width `max-w-3xl` (settings rule).
2. **Routes under `/api/sub-accounts/[id]/whatsapp/*`.** There is no
   `/api/sa` namespace; every tenant route in the repo is
   `/api/sub-accounts/[id]/…` and `requireSubAccountMember/Admin` anchor on
   that id. Read = member, write = admin, matching the sender registry.
3. **Provider seam with a fake, fenced exactly like GBP's.** CI's Playwright
   job cannot call Meta (no fixture WABA; Velocity is a live client), so the
   Graph calls sit behind `WhatsappSettingsProvider` with a `fake` arm
   selected by `WHATSAPP_SETTINGS_PROVIDER=fake` + loopback app URL +
   `WHATSAPP_FAKE_AGENCY_ID` = the fixture agency. The fake refuses any other
   tenant. Real-Meta correctness is covered by unit tests over the recorded
   responses below, not by E2E.
4. **Quality alert = hourly cron, alert only on a drop from GREEN.**
   `leadstack-whatsapp-quality` polls every cloud sender; the reading is
   stored on `whatsappCloudMeta.quality` (rating, nameStatus, status,
   checkedAt). A transition GREEN→YELLOW/RED (and only that) writes a
   `whatsappQualityAlerts` doc, pushes to the sub-account (existing
   `sendPushForEvent`) and emails the agency owner (the usage-meter owner
   pattern). Recovery back to GREEN updates the reading and closes the alert
   but does not email — GHL doesn't either, and an "all clear" mail every
   time Meta flaps would train people to ignore the real one.
   First reading (no prior) never alerts: there is nothing to have dropped from.
5. **Profile photo upload uses Meta's resumable upload on the token's own
   app.** `GET /app` with the stored system-user token returns the app id
   (probed: `1451493066882070`, "CrestaHQ Messaging"), so no env var is
   needed and a buyer's own app works unchanged. Photo ≤ 5 MB, jpeg/png.
6. **Display name is read-only**, as in GHL — Meta changes it through a
   name-review flow, not a profile write. `name_status` is shown instead.
7. **Message links: create / list / copy / QR / delete.** No edit — GHL has
   none either. QR served as Meta's SVG url, rendered inline.
8. **No outbound message anywhere in this subproject.** The only writes to
   Meta are profile POST, photo upload and message-link POST/DELETE, and
   they run only from the admin UI or its unit tests against the fake.

### Rejected

- A "Send test message" button on the header — outbound is a send-path
  change, human-gated, and blocked on Velocity anyway (#200 credit line).
- Polling quality on page load instead of a cron — an alert that only fires
  when somebody opens the page is not an alert.
- Storing the profile in Firestore — Meta is the source of truth and the
  form is read-modify-write against it; a cache would just drift.

### Highest-risk unknown

Meta's `profile_picture_handle` upload flow (`/{app}/uploads` → binary POST
→ `h:` handle) is the one call not covered by a recorded fixture, because
running it would change Velocity's live profile picture. It is unit-tested
against a mocked `fetch` and marked `// UNTESTED: live` until proven on a
fixture WABA.
